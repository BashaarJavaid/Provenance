# Threat Model

What Provenance protects against, what it explicitly does not, and the assumptions the whole model depends on. See [`ARCHITECTURE.md`](./ARCHITECTURE.md) for how each protection is implemented, and [`docs/adr/`](./docs/adr/) for why certain alternative approaches weren't used.

---

An explicit scope boundary is worth more to a technical reviewer than an implied claim of total coverage.

**The rule for this table: a row may only become more optimistic when the ROADMAP item that earns it is actually built and its `verify:` check passes.** Claims outrunning implementation is the exact failure this document exists to prevent. Until Phase 1 ships, every "Yes" below describes the *design*, not running code — each row names the ROADMAP item that turns it into a tested claim.

| Threat | Protected? | Notes |
|---|---|---|
| Prompt injection embedded in inbound data | **Yes — but not where you'd like the boundary to be** (items 25–27) | Model Armor screens (injection/jailbreak + SDP) and the Gemma sanitizer reduces input to typed facts — both are **filters that leak by design**; any architecture whose safety depends on a classifier recognizing adversarial text is one clever phrasing away from failure. The boundary is the gateway: it never reads the payload, cannot be persuaded, and scores the *typed action* on properties the action objectively has. The demo shows both outer layers leaking and the gateway holding at score 11 |
| Memory poisoning — a false belief asserted without verifiable evidence | **Yes (arithmetic)** (items 13–14) | `unverified_external_claim` evidence carries base weight **0.00**, so a bare assertion moves computed confidence by exactly nothing; a status flip additionally requires evidence of a `source_class` different from the one that established the current status. The defense is arithmetic, not a model's opinion about whether something smells adversarial |
| Confidence inflation by repetition | **Yes** (item 13) | Noisy-OR combines only *distinct source classes*, so restating the same observation five times scores the same as stating it once |
| Repeated poisoning attempts by a compromised agent | **Yes** (item 28) | Three rejected memory writes lacking verifiable evidence inside the rolling window → standing drops to `DEGRADED`: every subsequent proposal requires human approval regardless of risk score, and memory writes are rejected outright. Restoration requires explicit human reinstatement — the system never quietly forgives |
| Hallucinated action (fabricated tool, nonexistent target, free-form text) | **Yes — built and tested** (item 6) | Dies at schema validation before the gateway ever sees it; returned to the Planner exactly once, and a second malformed emission escalates the incident to a human. `provenance/action.py`; `tests/test_action.py` covers all three cases plus a wrong-kind target and a Planner misdeclaring reversibility, blast radius or tier. **The return-and-escalate half is live since item 9** — an edge in `provenance/incident.py`'s graph, with `tests/test_incident.py` asserting the Planner is never asked a third time |
| Plausible-but-wrong action that validates | **Yes (downstream)** (items 7, 19) | It still faces the risk table on objective properties and verification against its pre-declared success predicate; a wrong action that executes gets `REFUTED` and becomes a learned negative belief. **Live since item 10 as far as the refusal to learn:** the predicate is hashed onto the incident span *before* execution and onto the verification span after, and a `REFUTED` or `INCONCLUSIVE` outcome escalates and writes nothing. The *negative* belief on `REFUTED` is item 19 |
| Looping / runaway agent | **Yes (by construction)** (item 20) | Every incident carries a retry budget owned by the control loop in code — one bounded re-plan after `REFUTED`, then mandatory escalation. No agent owns its own iteration count |
| An agent talking its way past authorization (stated urgency, persuasive framing) | **Yes** (item 7 — tested) | The gateway's inputs are typed action fields, cryptographic identity, registry state, and table lookups. The proposal's prose is not an input. `ARCHITECTURE.md` §4.4 lists what each decision is *forbidden* to consume. `tests/test_gateway.py` asserts it directly: the same action with an urgent, authority-invoking `success_predicate` scores identically and lands on the same outcome |
| False institutional truth from unreliable verification | **Yes (by refusal)** (item 19) | Three-valued verification: `INCONCLUSIVE` writes **nothing** — no belief, no partial credit. Memory learns only from outcomes that could actually be confirmed. **Built and tested since item 10**, including the case §7.3 names but a cooperative model will never produce on cue: a verification agent that errors or times out is treated as `INCONCLUSIVE` by the control loop, which emits the span itself so an executed-but-unverified action cannot read as an incident nobody checked |
| Stale beliefs silently treated as current | **Yes** (item 29) | Every belief carries a decay schedule; the Staleness Sweeper re-verifies or downgrades to `UNKNOWN(reason=stale)` on expiry — excluded from recall and confidence computation, never deleted |
| Acting on a belief later proven wrong | **Yes (detective)** (item 15) | Retraction is a first-class transition that flags every action previously authorized on the retracted belief in the audit log for review. Detective, not preventive — the actions already happened. **As built:** the audit log is `authorizations/{id}` (`provenance/audit.py`), one record per authorized action citing the beliefs it rested on, written by the control loop after an approving gateway decision; retraction marks each matching record `flagged_by` before it appends its `RETRACTED` version. Two limits worth stating plainly: what a record cites comes from §6.6's recall, which returns empty until item 16, so today a real retraction flags nothing and the guarantee is proven against hand-seeded records; and the flag is a mark for a human to review, not an undo — nothing rolls the action back |
| Retrieval index leaking retracted/stale beliefs into reasoning | **Yes** (item 16) | The embedding index nominates belief IDs only; the store resolves each to its current version and drops `RETRACTED` / `UNKNOWN(stale)` before anything reaches the Orchestrator |
| PII leakage into institutional memory | **Yes** (items 25–26) | Model Armor's Sensitive Data Protection screens 150+ infoTypes at ingest; the sanitizer tokenizes what remains; beliefs reference entity IDs, never raw personal data |
| Class-belief generalization authorizing anything | **Yes (capped)** (item 23) | Class beliefs are hard-capped `ADVISORY ONLY`: confidence ≤ 0.75 and below the weakest constituent, may reorder hypothesis priority, may never authorize an action or evidence an entity-belief commit. A wrong class belief costs investigation order, never authorization |
| Model Armor / sanitizer bypass by a crafted payload | **Partial (by design)** | Expected and designed for — the demo payload itself clears Model Armor's threshold. Screening is defense in depth, never load-bearing; the row above ("prompt injection") describes where the real boundary is |
| Class beliefs derived from thin data (n=3) being simply wrong | **Partial (disclosed)** | Statistically thin generalization is bounded by the advisory cap, not prevented. A production version needs a real minimum-support policy (see ROADMAP, "Beyond the hackathon") |
| Verification failing the way production fails | **No (disclosed)** | Verification runs against a synthetic system whose state we control, so it cannot fail with production's ambiguity. The `REFUTED`/`INCONCLUSIVE` paths are implemented and exercised via fault injection (items 19–20), and the limitation is stated plainly in the submission |
| Compromised gateway / Memory Policy Engine host | **No** | If the process that *is* the determinism boundary is compromised, the attacker holds the signing keys and the authority. This is a GCP deployment/IAM hardening problem, not something the application layer can defend against |
| Insider human approver making a bad approve/deny call | **No** | The approval card makes the decision informed and the signed ledger makes it attributable and tamper-evident after the fact, but a legitimate approver approving a bad action is out of scope — that requires a multi-approver workflow (see ROADMAP, "Beyond the hackathon") |
| Colluding majority of evidence sources | **No** | Confidence assumes distinct source classes are independent. If the system observations, audits, and contractual records feeding a belief are all controlled by one adversary, the arithmetic is satisfied and the belief commits. Source-class independence is an assumption (below), not an enforced property |

**Assumptions** — every threat model implicitly relies on some things being true; stating them explicitly is what separates a scoped security document from an implied claim of total coverage:

- **The gateway is architecturally the only path to execution.** Load-bearing property 1 (`ARCHITECTURE.md` §1.1). Every protection above assumes no second path exists; CI and review must treat any bypass — including "temporary" test hooks — as a security regression, not a convenience.
- **The registry, gateway, and Memory Policy Engine run on uncompromised infrastructure** (Cloud Run services under project IAM). A compromised deterministic layer invalidates everything — see the "No" rows.
- **Distinct evidence source classes are independent.** The noisy-OR computation combines them as independent corroboration; a colluding majority defeats it (see the last "No" row).
- **The typed-action schema honestly describes the tools.** The tool registry, not the Planner, is authoritative for reversibility and blast radius; if the registry mislabels an irreversible tool as reversible, the risk table scores it wrong. Registry entries are hand-authored and reviewed.
- **The synthetic company is internally consistent and we control its state.** Verification predicates are meaningful against it; this is also the source of the disclosed verification-realism limitation.
- **The human approver is present and acting in good faith.** Held actions park indefinitely rather than auto-approving on timeout (fail closed), but the model does not defend against a malicious approver.
- **Google's managed services (Model Armor, Vertex AI, Firestore) behave as documented.** Their verdicts are logged and treated as filters/data stores, never as the boundary, which bounds the damage of a misbehaving service.
- **PortunusMCP's identity, RBAC/ABAC, and signing primitives are correct.** It is consumed as a library the way one trusts an auth framework; its own threat model lives in its own repo.
- **An agent keeps its own private key, and keeps it secret.** Item 7 resolved `ARCHITECTURE.md` §2.1's ambiguity in favour of the agent signing its own credential (`docs/adr/ADR-012`), so what the gateway proves is possession of the key registered against that `agent_id`. A leaked private half is a full impersonation of that agent, bounded only by its `tool_scope` and standing; rotation (`seed_registry.py --rotate`) bumps the version, and a credential minted for a superseded version is denied. There is no revocation list — `SUSPENDED` standing is the mechanism, and it is checked on every authorization because the registry is read at request time.
- **The Planner's private key reaches the deployed service as an environment variable.** `seed_registry.py` prints each private half once and stores it nowhere (ADR-010), so something outside the repo has to carry it; item 9 chose a Cloud Run environment variable, marked in the code with Secret Manager as the named upgrade path (`docs/adr/ADR-013` reason 9). Anyone who can read the service's configuration — a project IAM holder — can therefore impersonate the Remediation Planner, bounded by its `tool_scope` and standing. Stated here rather than left implied by "the agent keeps its key secret" above. `deploy.sh` writes the value through a mode-600 temporary file removed on every exit path, which keeps the PEM off the process table, not out of the service config.
- **The audit stream is served publicly, and what that publishes is deliberate.** `GET /trace` (item 11) is unauthenticated: item 11's own `verify:` line and item 36's cold judge both require a browser with no token to watch an incident, and a read spends nothing — which is the whole reason `/trigger` is guarded and this is not. It therefore publishes agent ids and versions, standing, action classes and targets, tiers, blast radii, the full §4.2 risk arithmetic, verification outcomes, belief ids and computed confidences, and decision signatures. What bounds it is §8.1's redaction rule: span attributes carry identifiers, hashes, enums and numbers and never content — no prompt, no model output, no rationale prose, no evidence text, and not even the success predicate (only its `sha256[:16]`). That rule is enforced at emit by `tests/test_telemetry_schema.py` and re-checked on the bytes the endpoint actually serves by `tests/test_app.py` and `scripts/verify_incident_one.py`. The route is read-only and reveals what the fleet *decided*, which is the point of an audit log; it reveals nothing about how to make it decide otherwise. If a later item ever puts content on a span, this endpoint is where it leaks.
- **The authorization ledger is stored, not published, and it holds no content either.** Item 15's `authorizations/{id}` records carry an agent id, an action class, a target, an outcome, a decision subject and signature, a timestamp, belief ids and review marks — identifiers, enums and signatures, the same discipline §8.1 imposes on spans, and no payload, prompt or rationale. No route serves it: it is read by `policy.retract()` and by scripts, and a surface that renders it is item 17's or item 31's, at which point this line is the constraint that applies. Retracting is the only thing that writes to an existing record, and it can only ever append a review mark.

- **The trigger stream is authenticated by a shared secret, and that is a spending control, not an authorization boundary.** `POST /trigger` requires a header matching `PROVENANCE_TRIGGER_TOKEN` and fails closed when unset. What it protects is the fixed model-token budget on a deliberately public service: it stops an anonymous caller looping the fleet. It grants nothing — a caller holding the token still cannot choose an action, a target or an outcome, because the gateway scores the typed action the fleet produced and the token is not one of its inputs (§4.4). A leaked token costs money, not authority.

- **Gateway decision signatures are verifiable within a process, not across restarts.** The signing key is generated per process and never persisted (`docs/adr/ADR-012` reason 8, marked in the code). A decision in the audit stream verifies against `gateway.public_key_pem()` from the same run, which is what the demo and a judge exercise; after a Cloud Run restart, earlier signatures can no longer be checked. Stated here rather than implied by the word "signed". The upgrade path is a PEM from Secret Manager.
- **Belief commit signatures carry the same limitation, and one more consequence.** `provenance/policy.py` holds its own per-process ECDSA key with the same `ponytail:` marker and the same Secret Manager upgrade path (`docs/adr/ADR-014`). Because a committed belief *stores* its signature, a belief written by one Cloud Run instance cannot be checked against a later instance's key — so the stored signature is tamper-evident only for as long as the process that wrote it lives. What a persisted key would buy is exactly the property §2.2 stage 6 implies and this does not yet deliver: that a belief's provenance is checkable by someone who was not there when it was written.
- **The executor re-checks the decision it is handed, so §1.1 property 1 does not rest on the graph's edge list.** `executor.execute()` verifies the signature, requires an approving outcome, and requires `decision.subject` to name the action's class and target (`docs/adr/ADR-014` reason 1). This closes the lift-and-shift path a signed APPROVE would otherwise offer — get a cheap rollback approved, present its decision beside an expensive action — but it is bounded by the assumption above: within one process. It defends against a wiring mistake and against a caller reusing a decision, not against an attacker who already holds the signing key (see the compromised-host row).
