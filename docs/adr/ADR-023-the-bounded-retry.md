# ADR-023 — The bounded retry: the loop owns the count, and a re-plan needs facts the first plan did not have

**Status:** Accepted (ROADMAP item 20). Answers the revisit clause in [`ADR-022`](./ADR-022-the-refuted-and-inconclusive-paths.md) and the "does not implement item 20's `REFUTED` retry budget" note in [`ADR-013`](./ADR-013-trigger-stream-and-incident-graph.md); implements `ARCHITECTURE.md` §7.1's second bullet, the retry half of §7.2's `REFUTED` row, and the §10 Bounded-retry row.

**Decision:** `resolve` becomes a routing node and the graph gains one edge, `(resolve, {"REPLAN": planner_agent, "DONE": halt})`. A `REFUTED` verification re-plans **exactly once** against a `REFUTED_RETRY_BUDGET` of 1 held on the control loop's scratch object; a second refutation escalates and the Planner is never asked again. `attempt` on the `verification.outcome` span becomes `refuted_attempts + 1` and finally exceeds 1. The retry's evidence is stamped with its own observation time, without which §2.2 would refuse the second commit `NO_NEW_EVIDENCE` and charge the agent standing for it. `provenance/policy.py` is unchanged.

**Reasoning, in order of weight:**

1. **Two budgets, not one, because §7.1 states two failures (primary reason).** The malformed budget is about the *shape* of an emission and is spent before the gateway sees anything; the refutation budget is about a remediation that was authorized, executed, and did not work. Collapsing them into one counter would mean a Planner that fumbled a field once loses the fleet's only chance to actually fix the service — which is neither bullet's intent. So `scratch.refuted_attempts` sits beside `scratch.malformed_attempts`, each with a budget of 1, and one incident may spend both: three Planner calls, still bounded. A global ceiling on Planner calls was the third option and was rejected for adding a number that no document names and that duplicates what the two counters already bound. `REFUTED_RETRY_BUDGET` lives in `incident.py` rather than beside `action.MALFORMED_RETRY_BUDGET`, because `action.py` is about what an Action is and a remediation that ran and failed is not a schema fact.
2. **The second refutation commits a `v2`, and making that reachable is the item's one non-obvious mechanism.** ADR-022's revisit clause predicted the shape correctly — a re-affirmation of `ROLLBACK_INEFFECTIVE` at the 0.50 door rather than a `v1` — and did not foresee what stood in the way. `_commit_belief()` stamped `observed_at` from the incident's frozen `now`, so both attempts produced a byte-identical `(source_id, observed_at)` pair and §2.2 stage 3 refused the second as `NO_NEW_EVIDENCE`. **That reason is in `COUNTED_REJECTIONS`**, so every bounded-retry incident would have charged `sre-infra-agent` a counted rejection for honestly reporting that its own remediation failed twice — three inside 24 hours is `DEGRADED`. That is precisely the pathology item 19 split `INSUFFICIENT_FOR_FLIP` off `BELOW_THRESHOLD` to prevent, arriving by a different door. The fix is that each attempt stamps its own observation time when `read_state()` returns: `now + (wall clock − wall_start)`. The caller's clock stays the base, so `tests/test_incident.py::test_two_incidents_sharing_a_predicate_store_two_distinct_observations` keeps pinning exact timestamps; only real elapsed time advances it. `policy.contributions()` clamps `age_days` at zero, so an observation microseconds ahead of `now` decays to `2^0` and the confidence is still exactly 0.60.

   A consequence worth stating: **offline this mutation is invisible.** `beliefs.TIMESTAMP` has second resolution and a `FakeLlm` finishes both attempts inside one second, so the offline retry path correctly hits `NO_NEW_EVIDENCE` — the same property `test_a_second_incident_supersedes_the_belief_the_first_one_wrote` already documented. Widening `TIMESTAMP` to milliseconds and adding a monkeypatchable clock were both considered and rejected: the first rewrites a stored format that `seed_belief.py`'s `SUP-042` chain, `beliefs.evidence_id()` and `verify_belief_inspector.py` all read, and the second adds a seam that exists only for tests. So the division is stated rather than hidden: **the offline suite proves the bound, and `scripts/verify_refuted.py` proves the `v2`.** Reverting the stamp leaves all 370 tests green and turns that script red, which was checked by doing it.
3. **The retry re-plans; it does not re-diagnose.** §7.2 says "planner re-plans with the refutation as input", so the edge returns to `planner_agent` and the Orchestrator and the domain agent do not run again. Routing to `domain_agent` instead would re-diagnose against the post-rollback state, which is richer and is not what the spec says, and doubles the model spend per retry. What the retry *does* get is the state the first plan could not have had: `{current_config_version}` is overwritten with the version the rollback actually deployed, because re-planning against a version the system no longer has is a re-plan aimed at the wrong world.
4. **`{refutation_feedback}` is a second slot, not a re-worded first one.** §7.1's re-plan feedback already taught the lesson that a re-plan with no feedback is only a second roll of the dice, and item 9 built `{malformed_feedback}` for it. Reusing that key would make its name a lie on this path and muddy the assertion in `test_the_replan_prompt_carries_the_rejection_reason`; renaming both to `{planner_feedback}` would edit working item-9 code for a word. Two causes, two slots, both written by the control loop and never by an agent.
5. **The retry prompt needed two facts the first plan did not, and both were found by running it rather than by design.** This is the honest history, because the shape of the failures is more instructive than the final text.

   *First*, told only that its remediation had been refuted, the Planner concluded the config was innocent and reached for the fleet's other tool — `DISABLE_COMPLIANCE_CHECKS(inventory-api)`, a supplier-scoped action aimed at a service. `action.validate()` rejected it as `UnknownTarget`, twice, and the incident escalated on the **malformed** budget having never made its second attempt: §7.1's first bullet working perfectly and item 20 starved by it. Two fixes followed, and the first was not enough on its own. `{known_action_classes}` now renders each class with the entity kind it acts on, straight off `tools.TOOLS` — a Planner asked to pick from a list cannot pick well without knowing what each option acts on, and that fact was simply being dropped on the way to the prompt. But a model that wants a different class resolves the conflict by keeping the target, so the retry text also states the target's kind as a fact, read from the tool registry via `tools.tool_for()`. Item 21's supply-chain agent gets the right word for free.

   *Second*, and sharper: handing the Planner the rate its failed attempt left behind invites it to declare success against that rate. Observed on the first live run that got as far as a second attempt — told the error rate was `0.38`, it declared "below 0.40", and its own refutation verified as `CONFIRMED` and the incident closed `RESOLVED`. This is item 11.5's hazard with the sign reversed. Item 11.5 gave the predicate a **floor** (a threshold at the nominal rate is unsatisfiable however well the remediation works); the retry needs a **ceiling** as well (a threshold at or above the measured failure is satisfied by the failure itself). Both bounds say one thing: a predicate must be satisfiable by success and unsatisfiable by the failure it is meant to clear. The ceiling is derived from `scratch.post_state.error_rate`, so it is a measurement rather than a constant.

   The alternative to both was to withhold the post-state from the retry, which would make §7.2's "with the refutation as input" hollow — the re-plan would be exactly the second roll of the dice item 9 already ruled out.
6. **No sixth span shape and no new attribute key.** `provenance.verification.attempt` was defined in item 2 and has been pinned to 1 since item 10; this is the first thing that moves it. "No third attempt occurs anywhere in the trace" is therefore proven by **counting** rather than by a new field: two `verification.outcome` spans numbered 1 and 2, two `authorization.decision` spans, two planning `reasoning.chain` spans, and nothing at 3. Four counts rather than one, because each alone is weak — two verifications alone would also be produced by a loop that re-verified one execution without going back through the gateway. A `provenance.incident.refuted_attempts` key mirroring `malformed_attempts` was the alternative and would have cost §8.1 an edit for a number the trace already carries. `ARCHITECTURE.md` §8.1 is unchanged; the streak since item 12 holds, with item 16's one exception.
7. **`IncidentResult` reports the last attempt, and gains one field.** The decision that was signed most recently, the action that ran most recently, and the belief version that stands. `refuted_attempts` is what tells a `/trigger` caller there was more than one; per-attempt records on the result object would be a documented shape change that `app.py`, both live scripts and the offline suite would all have to follow, to say what the trace says better.
8. **Two ledger records, and that is correct rather than a duplicate.** The retry goes back through `gateway.authorize()` — there is no path around it and item 20 did not build one — so two actions really were authorized, and §6.4 has to be able to flag either. `authorizations_for_target()` and the teardown already handle any number.
9. **`provenance/policy.py` is unchanged, which is item 19's finding holding a second time.** A re-affirmation is an ordinary `policy.commit()`; the engine decides what the retry may write exactly as it decides everything else. Having the control loop skip the commit on the second attempt was the tempting simplification and is the same shape item 19 rejected — the loop would pre-empt the engine and the refusal would vanish from the trace.
10. **`INCONCLUSIVE` is never retried.** §7.2 gives ambiguity its own row: escalate, learn nothing. Re-planning against measurements that settled nothing spends a model call on the same question, and would make `refuted_attempts` a count of something else. The retry condition is `== "REFUTED"` and not `!= "CONFIRMED"`, and a test holds the difference.

**What this deliberately does not do.** It adds no fourth fault-injection switch. The successful-retry path — attempt 1 `REFUTED`, attempt 2 `CONFIRMED` — is covered by `tests/test_incident.py` and nothing live, because `rollback_fails` is a switch and not a coin, so a live retry fails the same way twice. A "fails once" switch would cost a field on the frozen `company.FaultSwitch`, a flag on `inject_fault.py`, seeded documents and a teardown widening, to demonstrate a branch the offline suite already pins. It does not touch `provenance/policy.py`, `provenance/beliefs.py`, `provenance/telemetry.py`, `provenance/executor.py` or `THREAT_MODEL.md`.

**What this costs:** one graph edge, one constant, two `_Scratch` fields, one field on `IncidentResult`, one prompt slot and one line in the `execute` node. No new dependency, no new GCP resource, nothing that bills while idle. The `--refuted` half of `verify_refuted.py` goes from three `gemini-2.5-pro` calls plus one `gemini-3.5-flash` to **four Pro plus two Flash** — the retry is one more of each — and takes about 100 seconds. The `INCONCLUSIVE` half is unchanged at three Pro.

**A note on where the prompt work lives.** Three of this item's changes are sentences in a prompt rather than code, and all three were found live: the target-kind rendering, the target-kind restatement, and the predicate ceiling. That is the same division item 11.5 established and it is deliberate — the fix for a Planner that reasons badly is upstream in the prompt, and the check on it is downstream in a script (`verify_refuted.py` warns when the final predicate's threshold sits at or above the rate the failed rollback left behind). Putting a regex over natural language on the production path would spend a retry budget on something that is not a schema failure, which is exactly what the determinism boundary exists to keep out of the decision path.

**Revisit when:** item 21's second domain runs this loop and the retry's kind sentence gets its first non-`service` value; item 23's Memory Analyst proposes the status a retry commits, at which point `_LEARNS_FROM` and this edge stop being independent; item 30's park/resume makes a `HELD` retry possible, at which point "the last attempt" on `IncidentResult` means something a human interrupted; item 32's counterfactual A/B needs per-attempt token counts, at which point the trace's two planning chains have to be told apart by more than order; or a third §7.1 budget appears, at which point two hand-rolled counters want a shape.

**Alternatives considered:** one shared re-plan budget across both failure kinds (reason 1); a hard ceiling on Planner calls per incident (reason 1); `REFUTED_RETRY_BUDGET` in `action.py` beside the malformed one (reason 1); the control loop skipping the second commit, or reading `current()` to pre-empt it (reason 9, and item 19's rejected shape); widening `beliefs.TIMESTAMP` to millisecond resolution (reason 2); a monkeypatchable clock in `incident.py` so the offline suite could prove the `v2` too (reason 2); routing `REPLAN` to the domain agent for a re-diagnosis (reason 3); reusing `{malformed_feedback}`, or renaming both slots to `{planner_feedback}` (reason 4); withholding the measured post-state from the retry to avoid the threshold hazard (reason 5); a `provenance.incident.refuted_attempts` span attribute mirroring `malformed_attempts` (reason 6); per-attempt records on `IncidentResult` (reason 7); retrying `INCONCLUSIVE` as well, i.e. `!= "CONFIRMED"` (reason 10); a fourth `rollback_fails_once` fault switch to exercise the successful retry live ("what this deliberately does not do"); and a new `scripts/verify_bounded_retry.py` rather than extending `verify_refuted.py` (the `--refuted` half's assertions had to change either way, since turning the edge on makes a single-attempt run impossible — a second script would have duplicated its injection, its teardown and its trace read-back to assert a superset of what it already asserts).
