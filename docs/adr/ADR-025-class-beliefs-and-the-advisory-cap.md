# ADR-025 — Class beliefs: the Analyst recommends, the engine caps, and the cap is a refusal

**Status:** Accepted (ROADMAP item 23). Implements `ARCHITECTURE.md` §6.2 and the `class` / `derived_from` / `ADVISORY_ONLY` fields §3.2 predicted would "arrive with item 23"; discharges the Memory Analyst deferral item 14 recorded. Item 24 is what consumes the belief this produces.

**Decision:** `provenance/agents/memory_analyst.py` is §5.9's Analyst — a real `LlmAgent` that returns a class name and one sentence and **nothing else**. `policy.commit()` gains `scope` / `statement` / `derived_from`, all defaulting to the ENTITY behaviour, and enforces §6.2 itself: at least `CLASS_MIN_CONSTITUENTS = 3` constituents, every one of them a *current ENTITY belief carrying the status being generalized*, an evidence set **derived** from those constituents rather than proposed, and a confidence of `min(§4.3, CLASS_CAP = 0.75, weakest constituent − CLASS_MARGIN = 0.05)`. The advisory cap becomes a refusal: an `Evidence` whose `source_id` names a CLASS belief is `REJECT("CLASS_BELIEF_NOT_EVIDENCE")`, and that reason **counts against standing**. The Analyst runs from `scripts/seed_class_belief.py` and from no incident; `incident.py` is untouched.

**Reasoning, in order of weight:**

1. **The cap has to be a refusal, because two of its three enforcement points already existed and the third could not even be expressed (primary reason).** §6.2 says a class belief "may never be the evidence that authorizes an action or commits an entity belief". Item 16 already made the first half structural — `recall.Recalled` keeps `entity` and `class_beliefs` in separate fields and `incident.authorize` cites `recalled.entity_ids`, so a class belief cannot reach `authorizations/{id}.belief_ids` by type. The second half had nothing at all: `Evidence` has no belief field, so no proposal could name a class belief and therefore no code could decline one. A guarantee nothing can violate is not a guarantee, it is an absence of a feature — and item 28's whole arc is an adversary who *does* try the thing the design says is impossible. Making the attempt expressible and then refusing it is the only version of §6.2 that can be checked, and `scripts/verify_class_belief.py` checks it live.
2. **It resolves the cited id and refuses only CLASS, which is why the control test matters more than the positive one.** The cheap version is a shape check: refuse any `source_id` starting with `belief-`, no store read at all. It passes the item's verify line and forbids something no document forbids — §6.2 caps *generalizations*, and an entity belief cited as an observation is a different question this item has no mandate to answer. So the check resolves the id through `beliefs.current()` and looks at `scope`, and both `tests/test_policy.py` and the live script assert the **entity** case still commits. Without that control, "refuses class beliefs" and "refuses anything belief-shaped" pass identically.
3. **The check sits after the registry read, not at §2.2's stage 1, and the ordering is item 12's rule rather than a convenience.** §2.2 numbers typed-evidence validation first, and this is evidence validation. It also needs the store. Item 12 established that stage 2 physically precedes any store read — "an agent whose standing has not been checked does not get a read of institutional memory performed on its behalf" — and `tests/test_policy.py`'s fail-closed registry test is what pins it. Stage 1 as §2.2 writes it is *well-formedness*, which the frozen `Evidence` dataclass already guarantees at construction. So the check runs immediately after stage 2 and before stage 3's novelty read, and an unreadable store there is `STORE_UNAVAILABLE`, not a pass (§7.3).
4. **`CLASS_BELIEF_NOT_EVIDENCE` counts against standing; `INSUFFICIENT_CONSTITUENTS` does not.** The test is the one items 14 and 15 used to sort the other refusals: is this a statement about the evidence the agent brought, or about the store's state? Citing an advisory generalization as though it were an observation is the former — it is the memory-side twin of the poisoning attempt `BELOW_THRESHOLD` catches, and an agent doing it repeatedly is exactly what §3.4's counter exists to notice. "Fewer than three entity beliefs exist" is the latter, and shares `NOTHING_TO_RETRACT`'s reason for being excluded: counting it would let a mistimed proposal permanently degrade an agent for a fact about the corpus, and standing has no automatic restoration path. `COUNTED_REJECTIONS` goes to five; the poisoning arithmetic item 28 rests on is untouched.
5. **The class belief's evidence is derived inside the pipeline, and a caller that supplies its own gets an exception rather than a refusal.** If the Analyst could choose what its generalization rests on, §6.2's ceiling would be a ceiling over a set the model picked. So `commit(scope="CLASS")` reads the constituents' `evidence_ids`, unions them, and measures §4.3 over that — the Analyst never touches it, and `Generalization` has no field it could put evidence in. A caller passing both is not an adversary and not a proposal: `commit()`'s callers are our own code, so it is a bug, and the honest report of a bug is a `ValueError`, not a signed `REJECT` that would make a coding error look like a governance decision in the audit stream.
6. **`CLASS_MARGIN` is an invented number, and it is published here for the reason ADR-002 publishes the weights.** §6.2 says "always below its weakest constituent" and does not say by how much. The alternatives were both worse. `min(§4.3, 0.75)` plus a *refusal* when the result is not strictly below the weakest needs no invented number and, with constituents at 0.60 resting on one `verified_system_observation` each, refuses every class belief this system can currently produce — the cap would be unreachable rather than binding. A margin of 0.01 is the smallest number that makes "below" true and leaves a gap invisible in the belief inspector, which is where item 24 has to show it. 0.05 lands the seeded belief at **0.55**: above the 0.50 door, visibly below 0.75, visibly below 0.60. The number is arbitrary the way the base weights are arbitrary, and defensible for the same reason — it is inspectable, fixed, and in a document.
7. **The weakest constituent is measured live at `now`, not read off its stored confidence.** A version's `confidence` is frozen at its commit while the evidence behind it keeps decaying (item 17's two labelled numbers). Reading the frozen one would mean a class belief committed a fortnight after its constituents inherits a ceiling from evidence that no longer supports it, and the belief inspector would show a generalization above the live confidence of everything it generalizes. Recomputing costs nothing: the union read is already in hand, so each constituent's live number is a `policy.confidence()` over a slice of it.
8. **The shared status is what makes "sharing a structural signature" mechanical.** §6.2's phrase is a judgment, and an engine that checked only a count would be taking the signature on the Analyst's word — which is the shape §1.1 exists to eliminate. The status is the one part code can compare, so every constituent must carry the status being generalized. It is also what keeps a `RETRACTED` or `UNKNOWN` constituent out with no second rule: neither can match the status a live generalization asserts, so the explicit status-list check that was written first was deleted as redundant.
9. **The class name lives in `entity`, and there is no `class` field.** §3.2 lists `class` among a CLASS belief's fields, and `class` is a Python keyword — any dataclass field would have to be spelled differently from the document key, which is a mismatch on the one object whose stored form is the audit record. It would also duplicate: the id is `belief_id_for(entity)`, so a `class` field would carry exactly what `entity` and `belief_id` already carry. `tests/test_recall.py`'s CLASS fixtures have assumed this since item 16. `derived_from` is a real new field, defaulting empty for the reason `statement` does — an ENTITY version legitimately has none — and read with a `.get` so an ENTITY document is not malformed for lacking it.
10. **The Analyst is a seeder, not a graph node.** A node after each belief commit would put a `gemini-2.5-pro` call on every incident, add a node and edges to `build_graph()`, and add a failure mode to a path items 9–21 have verified live — to produce, on a corpus of three services, a proposal that is refused `INSUFFICIENT_CONSTITUENTS` on almost every run. It is also the wrong cadence: a generalization is a thing the organization does occasionally, not a thing an incident does. `scripts/seed_class_belief.py` runs it once, `incident.py` gained not one line, and the trace still carries the Analyst's reasoning span because the seeder configures tracing like any other live script.
11. **`step="generalization"` is not a telemetry change, and there is still no sixth span shape.** `telemetry.reasoning_chain()` takes `step` as a plain `str`, unlike the closed Literals around it, so the Analyst's span needed no vocabulary edit and `ARCHITECTURE.md` §8.1 was not touched. `belief.scope` has admitted `CLASS` since item 2 and this is its first non-ENTITY emitter. What did change is that `_finish()` reports the evidence the pipeline **measured** rather than what the caller passed — otherwise a class belief's span would say it cited nothing while `novel_count` said otherwise, which is a span contradicting itself.
12. **Two more tier-2 services, because there were not three entity beliefs to generalize.** `belief-inventory-api` is created and deleted by every run of `verify_incident_one.py`, so a class belief derived from it would dangle after the next regression; `pricing-api` must stay belief-free or item 24 — a deviation on an entity with empty entity memory — proves nothing; `checkout-api` was the only one left. `orders-api` and `search-api` extend the rationale `checkout-api` already carried in `company.py` and cost two dataclass entries, two comprehended fault switches and a `2` → `4` in one test. The alternative was constituents on ids that exist only in the belief store, which needs no fixture change and breaks `company.described()` for every reader of them.

**Two defects found live, both in what the Analyst was shown rather than in the engine.** Told only that three tier-2 services hold `CONFIG_REGRESSION_PRONE`, the first run generalized over "a high number of runtime dependencies" — a property nothing had given it. The clause forbidding terms it was not shown fixed that and produced the second: "having 'API' in the description is correlated with being prone to configuration regressions", a real shared attribute and a spurious class. Both are the same shortage — three rows differing only by name is not enough to generalize from — and the fix is that the seeder now states, in code, what the status *records*: that it is committed only after a rollback executed and verification CONFIRMED the deviation was gone. That is `sre_infra.seed_state()`'s `planner_context` posture, and with it the Analyst wrote the sentence the fixture actually supports. Item 11.5 and item 20 found their defects the same way and fixed them the same way: one clause, upstream, in the prompt.

**What this deliberately does not do.** It does not touch `gateway.py`, `risk.py`, `action.py`, `tools.py`, `executor.py`, `audit.py`, `recall.py`, `app.py` or `incident.py`. It does **not** add the advisory clause to the domain agents' instructions: `Recalled.summary()` has rendered class beliefs with an `[ADVISORY ONLY]` marker into `{recall_summary}` since item 16, `sre_infra.py` already interpolates it, and whether a recalled class belief actually reorders a hypothesis is item 24's verify line — item 18's lesson was not to claim causation that no A/B has measured. It does not give `GET /belief/{entity}` a class-belief surface: the route resolves by `belief_id_for()` and never touches `company.described()`, so it already serves the chain with `scope: "CLASS"`, and rendering `derived_from` as a linked breakdown is a surface item 24 or 31 earns. It does not filter `nominate()` by domain, which ADR-024's revisit clause anticipated; with one class belief in the store there is nothing for the filter to separate.

**What this costs:** one new agent file, two new scripts, one field on `BeliefVersion`, three constants and two `CommitReason` values in `policy.py`, a fourth registry record and two fixture services. One `seed_class_belief.py` run is one `gemini-2.5-pro` call; `verify_class_belief.py` is two embedding calls and no reasoning-model call. No new dependency, no new GCP resource, nothing that bills while idle.

**Revisit when:** a second class belief exists, at which point `nominate()` filtering by domain becomes a real question and `verify_class_belief.py`'s "exactly one class belief" premise has to change; item 24 measures whether the nomination actually moves a hypothesis, which is the first evidence that reason 10's cadence was right; item 29's Sweeper expires a class belief, which raises whether a constituent expiring should propagate to the generalization resting on it (nothing does today, and the class belief's own clock is what catches it); item 28 tries `CLASS_BELIEF_NOT_EVIDENCE` three times, which is the first live use of reason 4's standing cost; or a class belief is ever proposed by an agent rather than by a seeder, which is when reason 5's `ValueError` boundary is the wrong shape and the check has to become a refusal.

**Alternatives considered:** a shape-only belief-id check (reason 2); refusing every belief id, class or entity (reason 2); the check at §2.2 stage 1 before the registry read (reason 3); counting `INSUFFICIENT_CONSTITUENTS`, and not counting `CLASS_BELIEF_NOT_EVIDENCE` (reason 4); the caller supplying the class belief's evidence, and a signed `REJECT` rather than a `ValueError` for one that does (reason 5); no margin plus a refusal when the result is not below the weakest, and a margin of 0.01 (reason 6); the constituents' stored confidences as the ceiling (reason 7); a count-only minimum with the signature taken on the Analyst's word (reason 8); a `belief_class` field beside `entity` (reason 9); an Analyst node in the incident graph, and a deterministic signature extractor with no model at all (reason 10 and item 14's deferral); constituent beliefs on ids that exist only in the belief store, and three versions of `belief-inventory-api`'s chain as the three constituents (reason 12).
