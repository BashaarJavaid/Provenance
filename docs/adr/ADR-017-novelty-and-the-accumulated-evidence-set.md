# ADR-017 — Novelty is a pair, a version rests on everything it ever rested on, and nothing new is a refusal

**Status:** Accepted

**Decision:** §2.2 stage 3 is implemented as a comparison of `(source_id, observed_at)` **pairs**, resolved from the `evidence/{id}` documents the belief's current version cites. A proposal against an **existing** belief carrying no novel evidence is answered `REJECT("NO_NEW_EVIDENCE")` before confidence is computed. A superseding version's `evidence_ids` are its predecessor's **plus** the novel items, and §4.3's confidence is computed over that accumulated set. Evidence ids are **content-addressed** from the pair (`beliefs.evidence_id()`), so `append()`'s create-if-absent cannot store a document that disagrees with the pair its id names. `half_life_domain` stays one published number (30 days) until a second domain writes beliefs.

**Reasoning, in order of weight:**

1. **A `novel_count` that gates nothing is the cosmetic version of the boundary (primary reason).** ADR-002 exists because the common cheat is authority that lives in code on the diagram while the decisive input stays a model's opinion. The mirror failure is a check that is computed, emitted to the audit stream, and then not consulted. §6.3 states the requirement as a condition on the claim — "must carry evidence that is **new** … and verifiable" — and §2.2 orders novelty at stage 3, *before* confidence at stage 4. That ordering only means anything if stage 3 can terminate the pipeline, so it does. Fail-closed is the house default (§7.3) and this is the case it was written for: the belief in force stands, and the trace says why.
2. **Pairs, not ids, even though the id now encodes the pair.** With content-addressed ids the two comparisons agree, and comparing ids would be one set-membership test against `evidence_ids` with no reads at all. It is still wrong: §2.2 defines the check on the pair, and two callers already assign their own ids by hand (`tests/*`, `scripts/verify_belief_store.py`). Comparing ids would make the guarantee depend on an id-derivation convention that nothing enforces, so a hand-written id — or a future producer — could rename a duplicate past the check. Reading the documents costs a handful of gets on a path that runs once per incident, and it is the version that is true by construction rather than by discipline.
3. **A version rests on everything it ever rested on, because §6.3's own worked example does not otherwise work.** §3.2 renders belief #17 citing `ev-[118]` and its successor #42 citing `ev-[118,140,141]`. §6.3's legitimate update is an Aug-1 `contractual_record` followed by an Aug-15 `third_party_audit`, "confidence recomputes, threshold met" — which is 0.71 over the accumulated set and 0.55 over the audit alone, and the flip door item 14 must open is 0.70. A version citing only what its own proposal carried would leave §6.3's first case unreachable and hand item 14 a rule it cannot satisfy. Accumulation is also what makes the spec's *"same-source re-confirmation raises confidence via decay-reset"* true without new arithmetic: `confidence()` already takes the strongest (least decayed) item per source class, so a fresh reading displaces its own stale predecessor.
4. **Novelty is what keeps the accumulated set honest.** Accumulation on its own would let a belief grow by re-citation — the set gets longer, the decay clock resets, and nothing was observed. Stage 3 means the set can only ever grow by observations nobody has made before, which is why the two decisions are one ADR and not two. Together they are the bookkeeping half of the poisoning defense that §4.3's `max` is the arithmetic half of: repetition cannot inflate the number, *and* it cannot even reach the number.
5. **The gate is guarded on there being a predecessor, because the two refusals mean different things.** A first belief has no history to be novel against, so an evidence-free first claim is refused by ADR-002's arithmetic as `BELOW_THRESHOLD` at confidence 0.00 — the same door that refuses a bare `unverified_external_claim`. "Nothing new" is a statement about a belief that already exists. Collapsing them would make the audit stream report a repetition where there was none, and a test pins the distinction.
6. **The evidence id had to be fixed here, because item 13 is its first reader.** `incident.py` derived the id from `action.predicate_id()` — a hash of the success-predicate *text* — while `append()` writes evidence create-if-absent and swallows `AlreadyExists`. Two incidents whose Planner phrased the predicate identically therefore shared an id at different observation times: the second write was discarded, the version cited the same id twice, and the stored document kept the first run's `observed_at`. Nothing noticed while the id was only ever written. It is not cosmetic — `confidence()` decays from `observed_at`, so the survivor ages every later observation by however long ago the first incident ran, and stage 3 would be reading a timestamp nobody proposed. Deriving the id from the pair makes the collision unrepresentable rather than merely unlikely.
7. **One half-life, published, until something varies by domain.** §4.3's formula says `half_life_domain` and no document gave it a value, which is a real hole in ADR-002's "inspectable and fixed" defence — so 30 days is now published beside the weights it multiplies. Making it a per-domain table today would be a dict with one key: item 21 is when a second domain first writes beliefs, and that is when the table earns its existence.

**What this costs:** one `get` per cited evidence item on every commit against an existing belief — two or three for the life of this fleet, on a path that runs once per incident, and zero for a first belief. `read_evidence()` raises on a citation the store cannot answer rather than returning a shorter tuple, so a partially-written `evidence/` collection now fails a commit closed where it would previously have been invisible; that is the intended trade, since the alternative is a history with holes that calls a duplicate new. The accumulated `evidence_ids` grows by one per commit, which §3.2 already renders and item 17's inspector already has to display.

**Revisit when:** item 14 lands §6.3's different-source-class rule, which reads the source class that established the current status and may want that resolved from the same `read_evidence()` call stage 3 already makes; item 15's `RETRACT` needs to decide whether a retracted version's evidence stays in the accumulated set of anything that follows it (this ADR assumes the chain is only ever extended); ~~item 16's recall wants evidence resolved for a list of nominated beliefs, at which point the per-id `get` becomes a batched read~~ (**answered by item 16 with a no**: recall resolves *versions*, never their evidence — it needs a status and a confidence, both of which are on the version document, so `read_evidence()` gained no caller and no batching); §6.5's Sweeper starts recomputing confidence on expiry and needs the accumulated set to be the thing it recomputes over; or a second domain writes beliefs (item 21) and `half_life_domain` becomes a table.

**Alternatives considered:** emitting an honest `novel_count` and leaving the gate to item 14 (reason 1 — it ships the number without the authority, which is the shape ADR-002 forbids); excluding non-novel items from the confidence input and letting a stale re-affirmation fall out as `BELOW_THRESHOLD` (fewer moving parts, but it reports the wrong cause on the span and leaves §6.3's "must carry evidence that is new" unenforced); id set-membership novelty (reason 2); proposed-only evidence sets, as item 12 wrote them (reason 3); accumulating but leaving novelty ungated (reason 4); firing the gate on a first belief too (reason 5); leaving the predicate-hash evidence id and comparing only the proposed objects (reason 6 — the store then holds a pair the belief does not rest on); a per-domain `half_life_domain` table now (reason 7); and hashing the payload into the evidence id as well as the pair (§2.2 defines the same observation as the same pair, so a differing payload at one instant from one source is a store integrity question, not a novelty one).
