# ADR-026 — Incident #3: a cold entity's incident correctly ends without executing

**Status:** Accepted (ROADMAP item 24). Consumes the class belief [`ADR-025`](./ADR-025-class-beliefs-and-the-advisory-cap.md) produces and answers its revisit clause on whether the nomination moves a hypothesis; ADR-025 itself is not edited. Nothing under `provenance/` changed — items 8, 18 and 22's posture.

**Decision:** `scripts/verify_incident_three.py` wakes the fleet on an `error_rate` deviation on `pricing-api`, a tier-2 service with no config history, no entity beliefs and no prior incident. The class belief `belief-service.tier2` is nominated by the recall index and handed to the SRE agent; the diagnosis names a config cause; the Planner emits `ROLLBACK_CONFIG(pricing-api)`; the gateway approves at §4.2's `1 + 1 + 0 + 0 = 2`; and `executor.execute()` then **refuses**, because `known_good_version` is `None`, so the incident ends `ESCALATED` with no verification and no belief. That terminal state is the design, not a shortfall. `scripts/inject_fault.py` gains `--target`, defaulting to `inventory-api`.

**Reasoning, in order of weight:**

1. **`ESCALATED` is the correct outcome, and routing around it would cost more than it buys (primary reason).** §7.3's default posture is fail-closed, and `executor.execute()` raising on a missing known-good version is that posture already built (`tests/test_executor.py`) and already wired (`incident.py`'s execute node routes `HALT`). What the trace then shows is honest and, narrated, better than a green bar: the fleet generalized correctly from three services it *had* handled, proposed the right class of remediation for a service it had not, and the executor declined an action this entity cannot receive. The alternative reading — that the beat is broken unless something executes — mistakes the item's line, which is about the **nomination and the diagnosis**, for a remediation the roadmap never asked for.
2. **Nothing verifying is what keeps `pricing-api` belief-free, which is the premise every later run of this beat depends on.** §7.2 permits learning only from an outcome verification could settle, and nothing was executed to verify. So the belief-free property that makes this an entity with empty memory is maintained *by the same mechanism that stops the incident*, rather than by a teardown remembering to delete something. The script still asserts it — `restore()` returns a failure count and checks `beliefs/belief-pricing-api` before deleting anything — because a belief appearing there would mean the loop committed on an unverified action, which is a finding and not a cleanup.
3. **Rejected: a node or edge that halts before the Planner.** Stopping an incident whose target has no known-good version, or whose diagnosis recommends `NONE`, would be new code in `incident.py` — the module item 23 was proud of not touching and one of item 22's five counted files — plus, for a distinct terminal state, a `telemetry.IncidentOutcome` edit under item 2's condition. It would move a fact about *infrastructure remediation* (rollbacks need a version to roll back to) out of the executor, where §5.4's generality claim says domain knowledge belongs, and into the control plane. It buys a tidier trace over one that is already accurate.
4. **Rejected: give `pricing-api` a config gap**, and **rejected: a service-scoped tool that needs no known-good version.** Both already have their reasons on record — `company.py`'s own comment ("Give it a deploy history and the beat proves nothing") and ADR-025 reason 12 for the first, item 21's rejection of a third supplier tool for the second — and they are restated here because this is the item where they are actually tempting. A deploy history makes the class belief redundant, since the SRE agent's built-in hint would fire on the version gap; a second tool costs entries in `tools.TOOLS` and `risk.BASE`, a branch in `executor.execute()` and new fixture fields, to demonstrate an execute-and-verify path items 9–20 have proven four ways.
5. **The hypothesis is asserted, and the causation claim is exactly one step stronger than item 18's and no more.** Item 18 declined to claim memory caused the hypothesis because `sre_infra.py` carries its own config-regression hint, which fires on `inventory-api` with or without a recalled belief. Here that hint's precondition — *"the deployed config version is ahead of the last known-good one"* — is **false**: both are `unknown`. So `config_regression` on this fixture cannot have come from the hint, which is a materially stronger statement than item 18 could make. It is still not a measurement: one paired live run is an anecdote, and item 32's `--memory-disabled` A/B is where the number comes from. Pulling that forward would put a Phase 11 beat in Phase 7 against `CLAUDE.md` §2, and would double the model spend to produce a result that could flip between takes.
6. **`--runs N`, because the hypothesis is the one thing here a live model decides.** Everything else in the run is deterministic: the risk arithmetic, the routing kind check, the executor's refusal. The diagnosis is not, and item 11.5's precedent is that a one-in-three defect is invisible to a single run and both of the defects it fixed were intermittent. This beat is thirty seconds of video, so a flake rate is worth having before the demo depends on it. The measurement is a deliberate spend, made once.
7. **The per-run tally reads the in-process span buffer; the durable read-back runs once, on the last run.** `telemetry.BUFFER` holds the *same span objects* Cloud Trace gets rather than a copy (item 11), so nothing is weakened by reading three attributes out of it — and a ten-run sweep that polled Cloud Trace would pay ten four-minute waits to learn what a local read already knows. The Cloud Trace half still runs, because the durable record is what a judge opens, and it is last-run-only for item 11.5's reason: items 9–11 already pinned the span shapes.
8. **A local teardown rather than an import, and this is not a reversal of item 19.** `verify_refuted.py` imports its teardown from `verify_incident_one.py` because two restore paths over **one** fixture drift. This is a different fixture: `pricing-api`, whose fault switch, service document and ledger records no other script touches. What is imported is the target-agnostic half — `attribute()`, `load_private_key()`, `read_back()`, and `SWITCHES`, that last one precisely so a teardown cannot come to know about fewer §9 switches than exist. Parameterising `verify_incident_one.py`'s helpers by target was the alternative and would have put items 9, 10, 11, 11.5, 18 and 20 back on the regression list to prove a script-only change cost nothing.
9. **`--target` on `inject_fault.py` rather than a second script or a console flip.** §13's third beat needs an `error_rate` spike on `pricing-api` on camera, and the operator should reach it with the command they already use for incidents #1 and #2. It defaults to `inventory-api`, so every existing invocation and every documented line is unchanged in effect, and it validates the id through `company.service()` so a typo cannot write a `fault_injection` document for a service that does not exist. The verify script still injects and restores its own state, as every verify script does.

**The cosmetic artifact, stated rather than fixed.** `sre_infra.seed_state()` renders both config versions as the literal string `"unknown"` for a service with no history, and `planner_context` then instructs the Planner to state values literally — so a success predicate naming a version would read `is unknown`. It never executes, because the executor refuses first. Fixing it means behavioural lines in `sre_infra.py`, one of item 22's five counted files, which would put every incident path back on the regression list to tidy a string on a path that fail-closes anyway. Measured over ten runs: **five of ten** predicates named the version as `unknown`, so the artifact is frequent rather than incidental — which is the kind of thing one run cannot tell you, and the reason `--runs` exists. It costs nothing because the executor refuses first, and every one of the ten named an error-rate threshold of 0.015 or 0.02 against the 0.01 nominal, so item 11.5's floor held on a cold entity too.

**What this deliberately does not do.** It changes nothing under `provenance/` — no span shape, no attribute key, no control-plane path — so items 9–23's live evidence stands unaltered and `ARCHITECTURE.md` §8.1 is untouched. It does not add a `--memory-disabled` control run (reason 5; item 32). It does not render a class belief's `derived_from` as a linked breakdown in the belief inspector, which ADR-025 said "item 24 or 31 earns": item 24's line is about the trace, and `GET /belief/service.tier2` already serves the chain with `scope: "CLASS"` today. It does not filter `nominate()` by domain — still one class belief in the store, so ADR-025's revisit condition has not been met.

**What this costs:** one new script, one flag on an existing one, two offline tests, one ADR, one `ARCHITECTURE.md` §10 row. One run is three `gemini-2.5-pro` calls and one embedding batch — no Flash call, because the Verification Agent is never reached, which is itself asserted. No new dependency, no new GCP resource, nothing that bills while idle.

**Revisit when:** item 32's A/B measures what reason 5 declines to claim, at which point the "the hint could not have fired" argument becomes a control rather than the whole case; a second class belief exists and the script's single-nomination assertion has to change (ADR-025's clause); item 29's Sweeper can expire the class belief this run depends on, which would make a cold incident's recall empty and this script's premise false through no fault of the fleet; or `pricing-api` is ever given a config history, which is the one fixture change that silently turns this beat into incident #1 with a different name.

**Alternatives considered:** halting before the Planner on a target with no known-good version, and a distinct `IncidentOutcome` for it (reason 3); giving `pricing-api` a deploy history, and adding a service-scoped tool that needs no known-good version (reason 4); a `--memory-disabled` control run in this item (reason 5); a single run with no flake measurement (reason 6); polling Cloud Trace once per run (reason 7); parameterising `verify_incident_one.py`'s state helpers by target (reason 8); leaving `inject_fault.py` hardcoded, and a second fault script for `pricing-api` (reason 9); a `planner_context` clause special-casing an unknown known-good version (the cosmetic artifact).
