# ADR-022 — The `REFUTED` and `INCONCLUSIVE` paths: what a failure teaches, and what ambiguity does not

**Status:** Accepted (ROADMAP item 19). Answers the open fork in [`ADR-019`](./ADR-019-retraction-and-the-audit-ledger.md)'s revisit clause and the `REFUTED` half of [`ADR-014`](./ADR-014-execution-and-the-stub-policy-engine.md)'s; implements `ARCHITECTURE.md` §7.2's second and third rows and the §10 Verification row.

**Decision:** A `REFUTED` verification **commits** a belief with the domain-typed status `ROLLBACK_INEFFECTIVE` through the ordinary `policy.commit()` door — it does not retract, and the §2.2 pipeline gains no branch for it. The one change to `provenance/policy.py` is a *split of an existing refusal*: a flip that misses the 0.70 door while still clearing 0.50 is now `INSUFFICIENT_FOR_FLIP`, which is deliberately **not** in `COUNTED_REJECTIONS`. §9's `verification_ambiguous` switch reaches the control loop on `ExecutionResult` and routes the graph past the Verification Agent *after* the action has executed, so ambiguity is forced through §7.3's existing "executed and never verified" path rather than through a model asked to hedge on cue. `scripts/inject_fault.py` gains `--rollback-fails` and `--ambiguous`; `scripts/verify_refuted.py` is the live half.

**Reasoning, in order of weight:**

1. **A rollback that did not help does not disprove that the config regressed, so this is not a retraction (primary reason).** ADR-019 left the fork open: does a refuted verification retract the belief the confirmed run wrote, or write a negative one? §6.4 exists for "a belief committed in good faith that turns out to be **wrong**", and `CONFIG_REGRESSION_PRONE` is not wrong here — the deviation may well still be a config regression that this particular remediation failed to clear. What the fleet actually confirmed is a fact about the *remediation*, which is exactly how §7.2 words it: "rollback of v42 did *not* resolve this deviation." Retracting would erase a belief on evidence that does not bear on it, and would do it while flagging every action authorized on that belief for review — a false alarm manufactured by conflating two claims. `ADR-014`'s clause independently predicted the shape ("a second `_resolve` branch, not a reshape") and that is what shipped.
2. **The status names the remediation, not the negation of the other status.** `NOT_CONFIG_REGRESSION_PRONE` was the tempting symmetry and it asserts more than the evidence supports — the post-state says the rate is still 0.38 on v41, which is silent on what caused it. `ROLLBACK_INEFFECTIVE` is what a re-read of `services/inventory-api` can actually support, and it is also the more useful thing to recall: the next incident on this service wants to know that this remedy has been tried and did not work. §3.2 makes status domain-typed with only `UNKNOWN` and `RETRACTED` universal, so a second infrastructure-domain word needs no vocabulary change anywhere.
3. **The warm-chain refusal is §6.3 working rather than a gap, and it must not cost the agent standing.** `beliefs.belief_id_for()` gives one chain per entity, so on a service already carrying `CONFIG_REGRESSION_PRONE` the negative belief is a **status flip**: 0.70, plus at least one source class the chain does not already rest on. One fresh `verified_system_observation` is 0.60 in a class already present, so it is refused on the number and the confirmed version stands. That is the correct answer — one sensor reporting one reading should not be able to overturn a belief the same sensor established — and `_resolve` reaches it by handing `commit()` one different string and nothing else. The control loop does not choose between the engine's two doors; the engine decides. `tests/test_incident.py::test_a_refutation_cannot_flip_a_confirmed_belief_on_its_own` is what stops this being a paragraph nothing enforces.

   What that exposed is that **`BELOW_THRESHOLD` was carrying two incompatible meanings**, and §3.4's counter sits downstream of exactly the distinction it was eliding: "your evidence could not support a belief at all" (the poisoner, `unverified_external_claim` at 0.00) and "your evidence was good enough for a new belief and could not overturn one" (an honest agent at 0.60 meeting a higher door). The first must cost standing — it is item 28's whole arc — and counting the second would degrade an SRE agent for correctly reporting that its own remediation failed. So the refusal splits on `NEW_BELIEF_THRESHOLD`, which is precisely the line between the two cases: the poisoner is below **both** doors and keeps the counted name, and `INSUFFICIENT_FOR_FLIP` is new, uncounted, and reported with the same `threshold = 0.70` on the span. Item 14's principle was "the trace has to say *which* door stopped it"; this adds *how badly*, which is what the counter needed all along. `decision.reason` is a plain string on the span, so a new `CommitReason` is not a telemetry vocabulary change.

   Two things make the boundary the right one rather than a convenient one. `FLIP_UNSUPPORTED` needs no equivalent carve-out: an incident-written belief only ever rests on `verified_system_observation`, which caps at 0.60, so a warm refutation can never clear 0.70 and reach that check — it always meets the number first. And the alternatives to splitting the reason were both worse: a "do not count this" flag passed from `incident.py` would have the Policy Engine decide by *who is asking*, which is what §1.1 property 2 exists to prevent, and having the control loop read `current()` and skip the commit when it would be a flip would pre-empt the engine and erase the refusal from the trace entirely.
4. **Ambiguity is forced by making verification not happen, because a real model will not hedge on cue.** The literal reading of `verification_ambiguous` is a genuinely ambiguous post-state — half-fixed, say an error rate of 0.19. Against a predicate reading "below 0.015" a competent model answers `REFUTED`, not `INCONCLUSIVE`, so that live check would flip between two outcomes and the one it produced least often is the one under test. §7.3 already rules that a verification agent that errors or times out is `INCONCLUSIVE`, and item 10 already built the control loop that emits that span; the switch therefore routes `HALT` and lets that path run. The outcome is identical to the one the name promises and the mechanism is deterministic.
5. **The switch is read *after* `read_state()`, and that ordering is the whole claim.** Checked before execution, nothing would have run, and "no belief was written" would be explained by an incident that never got far enough — a green check proving nothing. Checked after, the rollback lands, the service is genuinely repaired, and the only thing missing is the confirmation. That is §7.3's row exactly: an executed action nobody could check. The live script asserts the repair (`v41`, rate back to nominal) precisely so the absent belief has only one explanation.
6. **The incident still ends `ESCALATED` on `REFUTED`, with a belief attached.** §7.2 pairs the negative belief with "second refutation → escalate, incident stays open", and the bounded re-plan that makes a *first* refutation something other than terminal is item 20's. So `IncidentResult` can now carry `outcome="ESCALATED"` alongside a committed belief, which is not a contradiction: the fleet learned something and the deviation is still there. `telemetry._ERROR_OUTCOMES` keeps `REFUTED` — a failed remediation is a failure — while `INCONCLUSIVE` stays off it, because ambiguity is an honest answer.
7. **`verification_ambiguous` rides out on `ExecutionResult` rather than being read again in the graph node.** It changes nothing the executor writes, which makes it an odd field on a result object; the alternative is a second Firestore read of a document `execute()` has already fetched in the same request, for one boolean. `ExecutionResult`'s existing contract — "the §9 switches, reported not hidden" — already covers it, and reading both switches in one place keeps ADR-009's request-time rule in one place too.
8. **Two halves in one script, because either alone is weak evidence.** A run asserting only "ambiguity wrote nothing" passes on a fleet whose memory is simply broken. A run asserting only "refutation wrote a belief" passes on a fleet that commits on anything. Asserting both against the same entity in one process is the only arrangement that fails for the right reason — item 16's control-record lesson and item 18's cold/warm contrast, applied again.
9. **`scripts/verify_refuted.py` imports its teardown from `verify_incident_one.py`, a deliberate break from convention.** Every other script in `scripts/` is standalone. These two are the only things that write `services/inventory-api`, its three fault switches, `beliefs/belief-inventory-api` and the ledger records for that target, and two restore paths over one fixture is a pair that drifts — the first time one learns about a new field and the other does not, a run leaves live state behind. `restore_service()` and `refuse_if_dirty()` were widened in this item to cover **all three** switches rather than only `error_rate_spike`, which is a correctness fix `verify_incident_one.py` needed the moment a second script could set the others.
10. **The flags set the other switches *alongside* the spike, and write every switch explicitly.** Neither beat is reachable without a deviation for the fleet to respond to, so `--rollback-fails` implies the spike. And every write goes through `baseline()` first, so a switch not named on this invocation is written **off** rather than left where the last run put it: two switches on at once is a state neither beat means, and `rollback_fails` left on would make the INCONCLUSIVE half's "the rollback worked" clause quietly false.

**What this deliberately does not do.** It does not *widen* `COUNTED_REJECTIONS` — the frozenset is unchanged at four reasons, and the new one simply is not in it. It does not touch `provenance/agents/verification.py`: item 11.5 established that loosening the honesty gate trades the property Phase 5 exists to demonstrate. It adds **no sixth span shape and no new attribute key** — the streak since item 12 holds, `belief_written=true` on a `REFUTED` span is a value the item-2 vocabulary already admits, and `ARCHITECTURE.md` §8.1 needed no edit. And it does not implement the bounded re-plan: `attempt` stays 1 on the verification span, which is item 20's to move.

**A naming tension, stated rather than renamed.** The switch is called `verification_ambiguous` and what it actually does is make verification not happen. §7.3 makes the two indistinguishable in outcome — an unanswerable verification and an unasked one are both `INCONCLUSIVE` — so the field earns its name by result if not by mechanism. Renaming it would touch the frozen fixture, `tests/test_synthetic_company.py`, `tests/test_executor.py` and the seeded Firestore documents, for a word.

**What this costs:** four lines in the `execute` node, one field on `ExecutionResult`, a two-entry dict in `incident.py`, and no new dependency, no new GCP resource and nothing that bills while idle. One `verify_refuted.py` run is three `gemini-2.5-pro` calls plus one `gemini-3.5-flash` for the REFUTED half and three Pro calls for the INCONCLUSIVE one — the Verification Agent is never invoked there, which is the point and is visible in the trace as five fewer spans.

**A consequence in a live script, worth knowing.** `scripts/verify_belief_store.py` used to observe that the three refusals it provokes on the way through items 12–14 were "exactly §2.2 stage 6's three", so the agent degraded in the middle of its own verification. One of those three is now uncounted, so it does not — the script asserts two counted entries and a standing of `GOOD`, and additionally that `INSUFFICIENT_FOR_FLIP` is absent from the window, which is the carve-out proven live. §3.4's "third counted refusal → DEGRADED" is unaffected and still proven in the same script by `standing_checks()`, where three unverifiable claims at 0.00 drive the counter 1 → 2 → 3 deliberately rather than incidentally.

**Revisit when:** ~~item 20's bounded retry makes a single incident produce two `REFUTED` outcomes~~ — **answered by [`ADR-023`](./ADR-023-the-bounded-retry.md)**, and the prediction held exactly: the second commit is a re-affirmation of `ROLLBACK_INEFFECTIVE` at the 0.50 door, superseding the v1 at the same 0.60, and `attempt` now reads 1 then 2. What it did not foresee is that the v2 was unreachable as written — both attempts stamped their evidence with the incident's frozen `now`, so §2.2 refused the second `NO_NEW_EVIDENCE`, which is a *counted* rejection and would have cost an honest agent its standing. Per-attempt `observed_at` is the fix; item 21 brings a second domain that needs its own negative status and `_LEARNS_FROM` stops being infrastructure-only; item 21 brings a second domain that needs its own negative status and `_LEARNS_FROM` stops being infrastructure-only; item 23's Memory Analyst proposes a status a model derived and both constants here become the thing it replaces; a refusal other than a flip turns out to need the same "honest but insufficient" distinction, at which point the split wants a rule rather than one branch; or `verify_incident_one.py` and `verify_refuted.py` need a third sibling, at which point the shared teardown deserves a module rather than an import.

**Alternatives considered:** retracting the confirmed belief on refutation (rejected — reason 1, ADR-019's other branch); a fresh belief chain per claim so the positive and negative could coexist (it would need a key like `belief-{entity}-rollback` and break §6.1's mechanical exact-key recall, which is the guarantee entity memory rests on); `NOT_CONFIG_REGRESSION_PRONE` as the status (reason 2); a hybrid that retracts when a belief exists and commits when one does not (reason 3 — it puts a choice between the engine's two doors inside the control loop, which §7.2 does not ask for); exempting `BELOW_THRESHOLD` from the counter wholesale (it would exempt the poisoner and gut item 28); passing a "do not count this" flag from the control loop, or having the loop pre-empt the flip by reading `current()` itself (both in reason 3); a half-fixed post-state to make the model genuinely unsure (reason 4); leaving `verification_ambiguous` unwired and forcing INCONCLUSIVE live by pointing the verification role at a nonexistent model (it demos nothing and leaves a declared switch dead against CLAUDE.md's owed-work list); reading the switch before execution (reason 5); a second Firestore read in the graph node instead of a field on `ExecutionResult` (reason 7); extending `scripts/verify_incident_one.py` a fifth time (every check function in its 1119 lines asserts `RESOLVED`/`CONFIRMED`/0.60/v41-with-rate-restored, so a refuted run inverts most of them and the diff is larger than a new file); and two separate scripts, one per half (reason 8 — and twice the teardown).
