# ADR-008 — One Cloud Run service, our own Dockerfile, no UI framework

**Status:** Accepted

**Decision:** The deployed surface is a **single** Cloud Run service (`provenance`, `us-central1`) running a plain FastAPI app we own (`provenance/app.py`), built from a Dockerfile in this repo, serving the UI as one static HTML file with no build step. Not ADK's `adk deploy cloud_run`, not `get_fast_api_app`, not a Node toolchain. `ARCHITECTURE.md` §11's "gateway, orchestrator, sweeper, and UI as services" describes the eventual shape; it is not a Phase 1 requirement, and splitting before anything needs a separate scaling profile buys four cold starts and one deploy script per component in exchange for nothing.

**Reasoning, in order of weight:**

1. **ADK's deploy path cannot express this project's install (primary reason).** `portunusmcp` must install as a second `--no-deps` step or pip silently downgrades `fastapi` to 0.115.6 out of `google-adk`'s supported range and drags in redis, sqlalchemy, asyncpg, alembic, mcp and uvloop (ROADMAP item 0.5, ADR-004). ADK's `_DOCKERFILE_TEMPLATE` has no hook for a second install, installs `google-adk` from PyPI rather than this repo, is `python:3.11-slim` against our `requires-python = "==3.12.*"`, and `COPY`s an agent folder. Owning eighteen lines of Dockerfile is cheaper than fighting a generated one, and it puts the constraint where a reader will hit it.
2. **ADK routes and delegates; it does not serve the gateway.** ADR-007 draws that line, and `get_fast_api_app` requires an `agents_dir` — there are no agents until Phase 3. Standing up an agent-discovery server with zero agents, to obtain a chat UI that is none of the six §8.2 surfaces, is scaffolding for its own sake. Phase 3 can mount ADK's app under a sub-path if it turns out to want one.
3. **The six surfaces are read-only views over one stream.** §8 commits every component to a single OpenTelemetry stream that the UI, the ledger, and the counterfactual panel all *read*. Rendering that is fetch-and-paint. A framework earns its build stage, its lockfile, and its second toolchain in CI when there is client state to manage; on day one there is none, and item 4 needs entities to render, not a component tree.
4. **Cost posture is a design constraint.** One service at `min-instances=0` bills nothing idle, which is what the $300 ceiling requires by default (`CLAUDE.md`, Cost ceiling). Four services multiply the surface on which someone later sets `min-instances=1` "just for the demo."

**Revisited at item 11 — no framework, and reason 3 held.** The update pattern is now known: the live fleet view and the gateway ledger fetch JSON from `GET /trace` once a second and repaint keyed by span id, over five span shapes, with no client-side state beyond a four-field form. That is still fetch-and-paint, so a build stage, a lockfile and a second toolchain in CI still buy nothing — see [`ADR-015`](./ADR-015-the-trace-ui.md), which also records why the UI reads an in-process span buffer rather than Cloud Trace. The single service is unchanged; item 11 added one read-only route to it and dropped `--max-instances` from 3 to 1, because the span buffer lives in the process that ran the incident.

**Revisit when:** item 30's approval queue arrives — the first surface that genuinely *writes*, and so the next honest test of reason 3; or when a component needs its own scaling profile, of which the Sweeper (Phase 9, already flagged in ADR-007's own revisit clause) is the likely first.

**Alternatives considered:** `adk deploy cloud_run` (generated Dockerfile is 3.11, agent-folder-shaped, and has nowhere to put the mandatory `--no-deps` step); `get_fast_api_app` with a placeholder agents directory (couples the skeleton to agent discovery before agents exist, and its dev chat UI is not a §8.2 surface); buildpacks with no Dockerfile (a plain `pip install` cannot express the two-step install at all); React + Vite (a Node toolchain, lockfile and build stage on day one for six panels that only read); server-rendered Jinja (a dependency, and awkward for surfaces that poll); four services now (§11's eventual shape, at four times the deploy surface and cold-start cost for no Phase 1 benefit).
