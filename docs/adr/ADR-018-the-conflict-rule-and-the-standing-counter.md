# ADR-018 — The conflict rule reads the classes a belief rests on, and only evidence-shaped refusals cost standing

**Status:** Accepted

**Decision:** §6.3's "a `source_class` different from the class that established the current status" is implemented as a **set difference over the current version's cited evidence**: a flip commits iff its novel items contribute a class that the accumulated set does not already carry, *and* confidence over that set reaches `FLIP_THRESHOLD = 0.70`. The two failures keep the two names §2.2 already had — `BELOW_THRESHOLD` carrying `threshold = 0.70`, and `FLIP_UNSUPPORTED` — so no `CommitReason` was added. §2.2 stage 6's "standing counter incremented" is `registry.record_rejection()`, called from `policy.commit()` on `BELOW_THRESHOLD`, `FLIP_UNSUPPORTED` and `NO_NEW_EVIDENCE` only; it appends to an **append-only, never pruned** `rejection_window` and applies `degraded_by_window()` to the appended list, writing `DEGRADED` through `set_standing()`. A registry that cannot be written is suppressed: the refusal stands.

**Reasoning, in order of weight:**

1. **"The class that established the current status" is the classes the version in force rests on, and stage 3 has already read them (primary reason).** ADR-017 left this as an explicit open question and answered it correctly by accident: `read_evidence(previous.evidence_ids)` runs at stage 3 for novelty, so the class set costs zero additional reads and is derived from the same objects the novelty check compares. The literal alternative — walk `history()` back to the version whose status differs from its predecessor and use *that* version's classes — needs a rule for what "established" means on a v1 that never flipped, and reads a chain that accumulation has already merged. Because `evidence_ids` accumulate, the two definitions coincide on every chain that has never flipped, and where they differ the accumulated reading is the stricter one: it counts every class that has ever supported the belief, so a flip cannot be built from a class that argued for the status it is overturning. Stricter is the right side to err on for a rule whose whole purpose is that one sensor cannot set and clear its own alarm.
2. **One source class cannot reach 0.70, which is what makes the class rule load-bearing rather than decorative.** The strongest base weight is 0.60 (`verified_system_observation`) and §4.3 collapses a class to its least-decayed item, so a proposal resting on a single class tops out below the flip door and is refused by the number alone. A same-class flip *above* 0.70 — ARCHITECTURE §10's row, and item 14's verify line — is therefore only reachable because a version rests on everything it ever rested on (ADR-017): the chain carries two classes, the proposal adds a third reading of one of them, and the class rule is the only thing left standing. That is precisely the case the live script constructs, and it is the case that fails if the class set is read off the proposal instead of off `known`.
3. **Two failures, two names, no new vocabulary.** A flip can miss on the number or on corroboration, and the trace has to say which — "not confident enough" and "one sensor setting its own alarm" are different facts about an agent, and item 28's panel renders the second. `belief.threshold` was already on the span (item 2) and already stored on the version, so emitting `0.70` makes `BELOW_THRESHOLD` self-describing without a new `CommitReason`, a new attribute key or a new enum value. Splitting into `FLIP_BELOW_THRESHOLD` / `FLIP_SAME_SOURCE_CLASS` / `FLIP_APPROVED` would grow a closed Literal by three and make `ABOVE_THRESHOLD` stop meaning "committed". ADR-016's revisit clause hoped `FLIP_UNSUPPORTED` would become "unreachable rather than merely unused"; the honest resolution is the opposite and better — it is now reachable and means exactly one thing, where before it meant "any status difference, for reasons not yet built".
4. **Only refusals that are statements about the agent's evidence cost it standing.** §3.4 counts "three rejected memory writes **lacking verifiable evidence**", not three rejections. `REGISTRY_UNAVAILABLE`, `STORE_UNAVAILABLE` and `VERSION_CONFLICT` are infrastructure — an outage, or a lost `create()` race — and standing has **no automatic restoration path**, so degrading an agent for a Firestore blip is a permanent penalty for someone else's failure wearing a security guarantee's clothes. `STANDING_NOT_GOOD` and `DOMAIN_NOT_HELD` are authority already refused; counting them would only re-degrade an agent that is degraded, and would make the window's contents a record of the consequence rather than of the cause. `NO_NEW_EVIDENCE` is included deliberately: it is a claim that added nothing, and excluding it would let a poisoner repeat one unverifiable pair indefinitely without ever reaching the counter — item 28's three attempts would refuse as "nothing new" and `DEGRADED` would never fire.
5. **The window is append-only, like everything else that records why.** `degraded_by_window()` filters by cutoff on read, so pruning buys nothing for correctness — and an entry that has stopped counting is still the record of *why* an agent degraded, which is what item 28's panel shows and what a human reinstating it needs to read. Pruning would also be a delete path in a subsystem whose entire design rests on never deleting (§6, ADR-016). The document grows by one small map per rejected write, on a path that runs once per incident.
6. **The counter write is best-effort and the refusal is not.** Nothing was committed either way, so a registry that cannot be written costs a missed increment rather than a wrong answer — and `policy.commit()`'s contract is that it never raises for a belief it declined to write, the same reason `gateway.authorize()` returns every terminal outcome as a `Decision`. Raising here would turn a correct fail-closed refusal into an unhandled exception out of the incident's `resolve` node, which reads as a crashed fleet rather than a defended one. `record_rejection()` still raises — it has to, to be suppressed — and `registry.py` keeps the fail-closed mapping every other writer uses.
7. **The span reports the standing that governed the decision, not the one it caused.** The agent was `GOOD` when the proposal was evaluated; the degradation is a consequence of the refusal and could not have been an input to it. `_standing()` already reads the `Agent` fetched at stage 2, so this is also the free option. `DEGRADED` becoming visible is the registry panel's surface (item 28), not this span's.
8. **`record_rejection()` takes the `Agent`, not an id, and lives in `registry.py`.** §1.1's fourth property is about reading standing *before deciding*, not about reading the same unchanged record twice inside one decision — the Policy Engine already holds the record from stage 2. Keeping the function in `registry.py` means one module owns every write to `agents/{id}`, and `set_standing()` stays literally what ADR-010 promised: the single writer of standing, which `record_rejection()` calls rather than bypasses. Which refusals count stays in `policy.py` (`COUNTED_REJECTIONS`), because that is a judgment about §2.2's pipeline, not about storage.

**What this costs:** one Firestore write per counted refusal, and a second when the third one degrades — on a path that runs at most once per incident. A flip now has to be *proposed* to be refused, so `FLIP_UNSUPPORTED` no longer catches every status difference; a proposal below 0.70 reports the number instead, which is a change in what the trace says about the same input. The suppressed `RegistryError` means a counter increment can be silently lost during an outage, so the window is a floor on how many rejections happened, never a ceiling — stated here rather than left to be inferred from "standing is earned and lost". And because the window is never pruned, an agent reinstated by a human carries its old entries forward; `degraded_by_window()`'s cutoff is what stops them counting, so a reinstatement that did not also clear the window would re-degrade on the next single rejection inside 24 hours. `scripts/verify_belief_store.py` clears both, and a human reinstating by hand must do the same.

**Revisit when:** item 15's `RETRACT` needs to decide whether retracting a version's evidence removes its class from the set a later flip is measured against (this ADR assumes the accumulated set is only ever extended); item 21 makes `half_life_domain` a table, at which point the flip threshold may want to be per-domain too and should not be, unless a document says so; item 23's class beliefs need a rule for whether a class belief's source classes can ever contribute to an entity-belief flip (§6.2 says advisory only, so the answer should be no, and nothing enforces it yet); item 28 renders the window and may want the `reason` vocabulary widened for display; or a human reinstatement path lands in the product rather than in a script, at which point clearing the window becomes a product decision rather than a fixture's.

**Alternatives considered:** resolving the established class by walking `history()` to the last status change (reason 1); using only the strongest-weight class of the current version as the "establishing" class (narrowest set, so flips are easiest — the weakest reading of a rule that exists to make flips hard); requiring the different class among *all* accumulated evidence rather than among the novel items (vacuous — a class already in `known` is by definition already in the accumulated set, so the check would always pass); new flip-specific `CommitReason` values (reason 3); keeping `FLIP_UNSUPPORTED` for both failures, as items 12–13 shipped it (reason 3 — the trace then cannot tell the two apart); counting every `REJECT` against standing (reason 4); counting only `BELOW_THRESHOLD` and `FLIP_UNSUPPORTED` (reason 4 — item 28's repeated identical claim never reaches the counter); pruning the window to the cutoff on write (reason 5); converting a failed counter write into `REJECT("REGISTRY_UNAVAILABLE")` (reason 6 — it overwrites the true cause, and the trace stops saying the evidence was insufficient); letting the counter write raise (reason 6); emitting the post-write `DEGRADED` on the commit span (reason 7); and extending `set_standing()` with an optional rejection parameter instead of adding a function (reason 8 — one writer that can write two fields which disagree is worse than two writers that cannot).
