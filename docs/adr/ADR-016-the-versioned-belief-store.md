# ADR-016 — The versioned belief store: a version subcollection, forward-only links, no pointer

**Status:** Accepted

**Decision:** A belief is a root document `beliefs/belief-{entity}` plus one **immutable document per version** at `beliefs/belief-{entity}/versions/{n}`, written with `create()` and never written again. Supersession links point **backwards only** (`supersedes: 1` on v2); `superseded_by` is derived on read. There is **no `current_version` pointer** — `current()` walks the versions until a read misses. Evidence is **normalised** to `evidence/{id}` and versions cite ids. `provenance/beliefs.py` is the store and decides nothing; `provenance/policy.py` stays §2.2's pipeline, and its `SUPERSESSION_UNSUPPORTED` refusal is retired in favour of a real superseding write — except for a **status flip**, which is refused as `FLIP_UNSUPPORTED` until item 14 owns the rule that governs one.

**Reasoning, in order of weight:**

1. **Append-only should be Firestore's guarantee, not our discipline (primary reason).** ROADMAP item 12's verify line is "committing a superseding belief leaves the old version intact and linked; nothing is ever deleted," and §6 rests the whole memory design on it. With one document per version and `create()` as the only write, overwriting a committed version is refused by the database — there is no code path in `provenance/` that can modify or delete one, and `tests/test_beliefs.py` asserts v1's stored dict is byte-identical after v2 lands. The rejected alternative, one document holding a `history` array, writes the entire chain on every commit through `update()`: append-only then means "our code happens not to shorten the list", and a single bug or stray script silently rewrites the reasoning trail the §6.4 audit flag depends on.
2. **Forward-only links, because a backlink is a second write to an immutable document.** Storing `superseded_by: 2` on v1 would mean touching a committed version after the fact — which makes "intact" mean "content intact, plus one field we added", and introduces a stored fact that can disagree with the chain if the second write fails. Version *n* is superseded iff *n+1* exists, so the backlink is one line in `history()` and cannot go stale. §3.2's rendering is a *view*, and this is the read that produces it.
3. **No pointer, because a pointer has a failure window and versions do not.** A `current_version` field on the root document is one read instead of two or three, at the cost of a gap between the version `create()` and the pointer `update()`: a crash in between leaves v2 written and the pointer at 1, and every later commit then collides on `versions/2` with no path back but a hand repair. Walking until a miss makes the newest existing version *the* current one by construction — nothing to reconcile, nothing to repair, no transaction. A Firestore transaction was the third option and buys the same property at the price of transaction support in `tests/test_registry.py`'s fake before a single item-12 test can run. At two or three versions per belief for the life of this fleet, the extra read is not a cost worth engineering against.
4. **The version document is written last, and that ordering is load-bearing.** `append()` writes the root document, then each `evidence/{id}`, then the version. A crash can therefore leave evidence nothing references yet — harmless — but never a version citing provenance the store cannot produce, which would be a belief that lies about what backs it. `tests/test_beliefs.py` asserts the order rather than trusting the comment.
5. **Evidence is normalised because item 13 needs one place to look.** §2.2's novelty check is a `(source_id, observed_at)` set-membership test, and §3.2 renders a belief's evidence as ids (`[ev-118, ev-140, ev-141]`). With evidence embedded per version, the same observation is copied into every version that re-cites it and "have we seen this?" becomes a scan of history with N copies to reconcile. Evidence documents are `create()`-if-absent, so re-citing an item is a no-op and never a rewrite — evidence is as immutable as the versions that cite it. This closes ADR-014's note that item 12 is what normalises it.
6. **A status flip is refused rather than approximated.** §4.3 puts a flip behind 0.70 **plus** §6.3's different-source-class rule, and neither exists until item 14. Shipping the number without the rule would be strictly weaker than either document: at 0.70 alone, one sensor could set and clear its own alarm, which is the single thing §6.3 exists to prevent. So a proposal whose status differs from the current version is answered `REJECT("FLIP_UNSUPPORTED")` carrying the computed confidence, and a re-affirmation — same status, new evidence — commits a real superseding version at the 0.50 door it already passed through. The refusal is a phase boundary made visible in the trace, not a limitation of the store, which supports either.
7. **The store and the pipeline are separate modules for the reason §1.1 property 2 exists.** `policy.py` decides and signs; `beliefs.py` persists and reads. Item 12's title pairs §3.3's typed Evidence with the store, so `Evidence` moved out of `policy.py` with it — which also gives item 13's novelty check, pure Evidence logic, an unambiguous home. The split mirrors the action side, where `gateway.py` decides over `risk.py`'s table and `credentials.py`'s assertions.
8. **Stage 2 still runs before the store is read.** §2.2 puts the registry check first, and it stays first: an agent whose standing has not been checked does not get a read of institutional memory performed on its behalf. The cost is that a refusal at stage 2 reports `belief.version = 1` and no `supersedes`, because the engine never learned what version was at stake — the span's `decision.reason` says plainly that the write never reached the store, and `tests/test_policy.py`'s fail-closed registry test is what pins the ordering.
9. **`Action.evidence_refs` is still not checked against this store, and ADR-011's note is answered "no".** §2.1's seven stages contain no evidence-existence check, and adding one would be a gateway stage no document defines, a second collection read per authorization, and — today — a denial of every real proposal, since the Planner coins the ids it cites. §2.2 stage 1's "must reference existing evidence IDs" is about the *memory* pipeline, and there the engine satisfies it directly: it writes the evidence documents the version it commits cites.

**What this costs:** two to three Firestore reads per `current()` instead of one, and one more write per commit than the embedded shape (the root document, once per belief). The decay clock (`half_life_days`, `expires_at`, `on_expiry`) is written now though the Sweeper that consumes it is Phase 9's, so that beliefs committed in between are not a backfill problem for it — three constants, no branch. `policy.py`'s per-process signing key is unchanged and carries the same `ponytail:` debt as the gateway's, with Secret Manager as the named upgrade path.

**ADR-014's revisit clause, answered.** Its reason 2 — the Policy Engine as a stub that refuses rather than approximates — is gone: `SUPERSESSION_UNSUPPORTED` is removed from `CommitReason` rather than left unused, and a second version of a belief is now a normal outcome. What remains stubbed is named there and unchanged here: the novelty check (item 13), §6.3's conflict rule and the standing-counter write (item 14), and `RETRACT` (item 15).

**Revisit when:** item 14 lands the flip rule (`FLIP_UNSUPPORTED` should then become unreachable rather than merely unused — this ADR's own reason 6 turned on ADR-014's precedent for exactly that); item 15's retraction needs a `RETRACTED` version that is a transition rather than a status (the version shape already carries it as one); item 16's recall needs the store to resolve currency for a list of nominated ids, which is `current()` per id and may want a batched read; or a belief ever needs versions in the hundreds, at which point the walk becomes a query and the root document earns a pointer.

**Alternatives considered:** one document per belief with a `history` array (reason 1 — and it is §3.2's rendering, which is why it is the tempting one); flat `beliefs/belief-{entity}-{n}` documents plus a `beliefs_current/{entity}` pointer (reasons 1 and 3 — it keeps item 10's ids at the price of putting "which version is current" in a different document from the belief); stored `superseded_by` backlinks (reason 2); a `current_version` pointer, with and without a Firestore transaction (reason 3); evidence embedded in each version, as item 10 wrote it (reason 5); keying beliefs `belief-{entity}-{domain}` (nothing in the roadmap writes two domains about one entity, and the seeded cast's entity ids already imply their domain — ADR-010's and ADR-011's rule that a key changes when a caller exists); committing a flip at 0.50 in the window before item 14 (reason 6); bringing §4.3's 0.70 forward without §6.3's source-class rule (same reason, from the other side); building the store and leaving `policy.py` refusing until item 14 (it would ship a module with no production caller and prove item 12's verify line only in isolation); and a gateway stage resolving `evidence_refs` against `evidence/{id}` (reason 9).
