# ADR-019 — Retraction is §6.4's rule, not §6.3's, and flagging needs a ledger nothing else was going to build

**Status:** Accepted

**Decision:** §6.4's retraction is a second public entry point, `policy.retract()`, sharing `_decide()` with `commit()` through a `retracting` flag. It writes an ordinary superseding version whose `status` is `RETRACTED`, with `BeliefOutcome = "RETRACT"` on the wire. §2.2 stages 2 and 3 apply unchanged; stages 4 and 5 swap in §6.4's gate — **confidence over the disproving evidence alone** against `NEW_BELIEF_THRESHOLD = 0.50`, plus a class test requiring at least one disproving item whose published `BASE_WEIGHT` is >= the strongest class the version in force rests on. §6.3's different-source-class rule does **not** apply. Two `CommitReason` values are added: `RETRACTION_UNSUPPORTED` (counted against standing, the fourth member of `COUNTED_REJECTIONS`) and `NOTHING_TO_RETRACT` (not counted). §6.4's third bullet is served by a new `authorizations/{id}` collection in `provenance/audit.py`, written by `incident.py` after an approving gateway decision and citing whatever `recall()` returned; `audit.flag()` appends a `flagged_by` entry to every record citing the retracted belief, and it runs **before** the version is appended. Nothing subtracts: the `RETRACTED` version cites the accumulated set plus the disproving items, and no class ever leaves the set a later flip is measured against.

**Reasoning, in order of weight:**

1. **Nothing linked an action to a belief, and no honest version of §6.4's third bullet exists without one (primary reason).** `Action` carries `evidence_refs` — evidence ids, §3.3 — and `gateway.Decision` carries a subject, a signature and a risk score. Neither names a belief, and `executor.ExecutionResult` does not either. The only belief ids anywhere in the system are `recall.belief_ids` on the `reasoning.chain` span, which records what memory *nominated* during diagnosis and is not durable. The available join without new storage is `target == entity` inside the window the retracted version was in force, and it is a different and weaker claim: it flags actions that merely touched the same entity, it cannot pin which version was in force, and it cannot distinguish "this belief's status informed the plan" from "this incident happened to be about this service". §6.4's whole rhetorical weight — "a system that can be wrong and knows *which* of its past decisions rested on the wrong thing" — is exactly the distinction the heuristic erases. So the ledger is the minimum, and the honest cost is stated rather than hidden: `recall()` is item 16's and returns `()` today, so every record this fleet writes cites nothing and every real retraction flags zero actions. The mechanism is proven with scripted records, the posture item 8 used to prove denial-by-registry before any agent existed and item 14 used for the conflict rule before the Memory Analyst did.
2. **§6.3 hands the disproven case to §6.4 explicitly, so §6.4 is the rule and not an addition to it.** §6.3's three cases end with "*Disproven belief.* Retraction — see §6.4", which is a delegation, not a cross-reference. Applying both would make a same-class retraction impossible — and a sensor reporting that what it previously reported was wrong is the *paradigm* case §6.4 exists for. §6.3's rule is "one sensor cannot both set and clear an alarm", which is about a sensor asserting the opposite state; §6.4's is "at least as strong as what established the belief", which is about a sensor withdrawing its own claim. They are different rules for different acts, and §6.4 names its own.
3. **0.50 over the disproving evidence alone is the only reading in which every clause means something.** Over the *accumulated* set any threshold is free — that set has already cleared one, and a retraction citing everything the belief ever rested on would pass 0.70 without the disproving item contributing anything. At **0.70** over disproving-only, the strongest single class is 0.60, so two source classes are always required and §6.4's "a source class at least as strong" bullet becomes dead text describing a case that cannot occur. At **0.50** the arithmetic states §6.4's bullet exactly: one `verified_system_observation` (0.60), `third_party_audit` (0.55) or `contractual_record` (0.50) suffices, while `agent_inference` (0.15) and `unverified_external_claim` (0.00) cannot retract anything. Dropping the number entirely — §6.4 does list three bullets and name no threshold — would leave the one path that *erases* institutional memory as the only path in the system with no arithmetic guarding it, which is the wrong exception to make. The two rules are also genuinely independent: `third_party_audit` at 0.55 clears the door and still fails the class test against a belief established at 0.60, which is the case the live script and `test_a_strong_enough_number_still_fails_the_class_test` both construct.
4. **The strength baseline is the strongest class the version in force rests on, and `BASE_WEIGHT`, not the decayed weight.** This is item 14's reading of §6.3's near-identical phrase applied to §6.4's, and it costs zero additional reads because stage 3 already resolved `read_evidence(previous.evidence_ids)` for the novelty check. Because evidence accumulates, it is also the stricter of the readings available: it counts every class that has ever supported the belief, not only the one that last changed it. Comparing *decayed* weights instead would make "class" mean "item" — which is not what §6.4 says — and would make the rule time-dependent, so a belief could become progressively easier to retract by nothing but sitting there, or harder, depending on which side aged faster.
5. **Nothing subtracts, which answers ADR-017's and ADR-018's revisit clauses with a "confirmed" rather than an exception.** Both ADRs assumed the accumulated set is only ever extended and flagged retraction as the case that might break it. It does not: the `RETRACTED` version cites the accumulated set plus the disproving items, so §3.2's history block stays the full reasoning trail and `read_evidence` can still resolve every citation. Resetting the set at a retraction would make a committed version stop being able to produce its own provenance; dropping the retracted classes from the flip-comparison set would need a second read path to compute a set that is one set today. The consequence is deliberate and strict: re-asserting a retracted status is an ordinary flip needing 0.70 *and* a class the whole chain does not already carry, so a belief cannot be retracted and reinstated by the same two sensors trading turns.
6. **Flag first, then append — the same ordering rule `beliefs.append()` already follows, for the same reason.** `append()` writes evidence before the version that cites it because a crash leaving unreferenced evidence is harmless while a version citing evidence the store cannot produce is a belief that lies. The symmetric asymmetry holds here: a flag pointing at a retraction that never landed is a false alarm a human reviews and dismisses, while a retraction whose actions were never flagged is a decision resting on a wrong thing that nobody knows about — the exact failure §6.4 exists to prevent. So an unwritable ledger is `REJECT("STORE_UNAVAILABLE")` with no version appended (§7.3), never a quiet success. The same asymmetry drives the incident side: a ledger write that fails after an approval leaves an authorization no retraction can ever flag, so `incident.py` fails closed — routes `HALT`, ends `ESCALATED`, executes nothing. The belief store is the same Firestore, so an incident that cannot write the ledger could not have committed its belief either; this costs a rollback during an outage and buys the guarantee holding for every action that did happen.
7. **`RETRACTED` is a status *and* `RETRACT` is a transition, which is what ADR-016's revisit clause was actually asking.** §3.2 lists `RETRACTED` among the universal statuses; §6.4's prose and the `BeliefOutcome` Literal (item 2) treat retraction as an outcome beside COMMIT and REJECT. Both are true and they describe different things: the outcome is what the Policy Engine decided and what the span carries, the status is what the store now holds. Modelling it as only a status would mean `commit(status="RETRACTED")` — a caller writing a string triggers a Firestore side-effect on unrelated records, and stage 5 becomes conditional inside a function whose docstring promises a fixed stage list. Modelling it as only a transition would need a version shape that is not a version. Two public doors over one internal pipeline is the smaller surface.
8. **The ledger is a new module, not part of `beliefs.py`, because `flag()` is an `update()`.** `beliefs.py`'s entire contract is that no function in it modifies or deletes a committed document, and two tests exist solely to keep that true. An authorization record is not a belief — §6's append-only rule is about what the organization believes, and marking an already-written record for human review neither rewrites history nor changes a belief. Keeping the update in `audit.py` is what lets "nothing under `provenance/` modifies or deletes a belief version" stay literally true after item 15 rather than becoming a claim with an exception attached.
9. **Only authorized actions are recorded, and the record is written by `incident.py`, not the gateway.** §6.4 flags what was "previously **authorized**" — a HELD action parked on a human and a DENIED one never happened, and neither rests on a belief in a way that needs reviewing. **Corrected in part by [`ADR-032`](./ADR-032-the-approval-queue.md) §10 (item 30):** this is right about an *agent-stage* denial, which nobody was asked about, and about an action still parked. A **human's** verdict is the opposite case — somebody was asked and answered — so a resumed approval *and* a resumed denial both write a row, carrying a new `approver` field. The writer is still `incident.py`, now from `resume()`. The write lives in the control loop because `gateway.authorize()` is a pure function today: adding a Firestore round-trip to it would give a failed write a path to influence an authorization outcome, and would put I/O in the one module whose testability rests on having none. `executor.execute()` was the other candidate and is wrong for a different reason — it would miss an approved action that never executed, which §6.4's wording covers.
10. **`RETRACTION_UNSUPPORTED` costs standing; `NOTHING_TO_RETRACT` does not.** §3.4 counts "rejected memory writes **lacking verifiable evidence**", and item 14's test for membership is whether the refusal is a statement about the agent's evidence. Bringing evidence too weak to retract is exactly that. Aiming a retraction at a belief that is absent or already retracted is a statement about the store's state — a mistake, but not the kind §3.4 counts, and counting it would let a typo or a race degrade an agent permanently, since standing has no automatic restoration path.

**What this costs:** one Firestore write per authorized action, on a path that runs once per incident, plus one query and up to N updates per retraction. A new collection outside the three ADR-016 named, and the first `update()` anywhere in the memory subsystem — quarantined in `audit.py`, but real. `CommitReason` grows by two, and `COUNTED_REJECTIONS` from three to four, so a fourth kind of refusal can now degrade an agent. The incident path gained a fail-closed dependency: a Firestore outage between the gateway's approval and the ledger write now stops a rollback that would otherwise have worked, which is a deliberate trade of availability for the auditability §6.4 promises. The offline test double grew a `where`/`stream` pair — the first query support it has ever needed. And the honest limitation, stated in `audit.py`'s docstring rather than left to be discovered: until item 16, every record cites no beliefs, so a retraction of a real belief flags nothing, and §10's retraction row is proven with hand-seeded records.

**Revisit when:** ~~item 16 makes `recall()` return real belief ids, at which point the ledger starts carrying them and the flagging becomes live rather than scripted — and the question of whether an action should cite the belief *version* it saw, not just the id, becomes answerable~~ (**answered by item 16**: the ledger carries real ids and cites **entity beliefs only**, since §6.2 makes a class belief advisory and therefore never what an action rested on. The version question is now answerable and the answer stayed *id*: `flag()` already records the version in force at retraction time, and citing the version *seen* would flag on a comparison — did the action see the version that was later retracted, or an earlier one — that §6.4 does not ask for. Revisit it if a belief is ever retracted at a version an action predates); item 19's `REFUTED` path becomes the first non-scripted producer of a retraction and has to decide whether a refuted verification retracts the belief the confirmed run wrote or writes a negative one beside it; item 29's Sweeper decides whether a `RETRACTED` version's decay clock means anything, since item 15 writes the same three constants on it with no branch; item 17's belief inspector or item 31's cards need to render `flagged_by`, at which point the flag may want a span so it is visible live rather than only in Firestore; or the ledger grows past the point where an unindexed `array_contains` query is free, which at demo scale it is not near.

**Alternatives considered:** flagging by `target == entity` and a time window, with no new stored link (reason 1 — flags actions that merely touched the same entity, and cannot name the version); adding `belief_ids` to `gateway.Decision` and a new `action.belief_ids` §8.1 attribute, scanning the span stream at retraction (reason 1 — the buffer is bounded and in-process and Cloud Trace is not queryable from here, so "every action" cannot be enumerated); deferring the flagging half to item 16 entirely (leaves §10's retraction row unproven while the roadmap says item 15 is next); applying §6.3's different-class rule to retraction as well (reason 2 — makes the paradigm case impossible); computing the retraction's confidence over the accumulated set (reason 3 — the door becomes free); putting the retraction door at 0.70 (reason 3 — §6.4's bullet becomes unreachable); no threshold at all (reason 3); using the classes of v1 as the strength baseline, the literal reading of "the class that established the belief" (reason 4 — a belief later corroborated by a stronger class could be retracted by the weaker original, and it needs a `history()` walk where the in-force reading is free); comparing decayed weights (reason 4); resetting the accumulated set at a retraction (reason 5); dropping the retracted classes from the flip-comparison set (reason 5); appending the version before flagging, or flagging best-effort as `record_rejection()` is (reason 6 — silently weakens the one guarantee the item adds); `commit(status="RETRACTED")` as a single public door (reason 7); making retraction terminal so a chain cannot be extended past it (a rule no document states, needing a new refusal and a guard in `beliefs.append()`, when item 16's recall already drops `RETRACTED` from nomination); folding `record`/`flag` into `beliefs.py` (reason 8); writing the ledger record from `gateway.authorize()` or `executor.execute()` (reason 9); recording held and denied decisions too (reason 9 — they were not authorized); counting `NOTHING_TO_RETRACT` against standing (reason 10); a single `RETRACTION_UNSUPPORTED` covering both new failures (the trace stops saying which of two very different things went wrong, against item 14's precedent); an append-only `audit_flags/{id}` collection instead of a field (a second collection for a fact that belongs on the record it describes, and a join to read it); and a sixth `provenance.audit.flag` span shape (§8.1 change for something with no durable record behind it — the streak of no new shape and no new attribute key since item 12 holds).
