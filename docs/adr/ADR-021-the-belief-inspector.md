# ADR-021 — The belief inspector: the UI's second data source, and the seeded chain behind it

**Status:** Accepted (ROADMAP item 17). Amends [`ADR-015`](./ADR-015-the-trace-ui.md)'s "the UI reads that one stream"; implements the belief-inspector surface of `ARCHITECTURE.md` §8.2 and the §9 promise that `SUP-042` becomes AT_RISK through the belief store or not at all.

**Decision:** `GET /belief/{entity}` is a new **unauthenticated** route on the one service, reading Firestore through `beliefs.history()` and `beliefs.read_evidence()` and serving the whole chain, the evidence every version cites, and §4.3 recomputed as of now. §4.3's per-class arithmetic gets one implementation, `policy.contributions()`, which `policy.confidence()` is defined in terms of. `scripts/seed_belief.py` writes the `SUP-042` belief as **two versions through the real `policy.commit()` pipeline** — `FLAGGED` at 0.575, superseded by `AT_RISK` at 0.770 — create-if-absent, with no `--reset`.

**Reasoning, in order of weight:**

1. **The span stream structurally cannot serve this, which is why the second source exists (primary reason).** §8.2 asks the inspector for evidence, the arithmetic behind a computed confidence, a supersession chain and a decay clock. Every one of those is *content*: `verifiable_by` is a sentence, `source_id` names a system, and the arithmetic is only inspectable if the items behind it are nameable. §8.1 keeps content off spans deliberately, and `tests/test_telemetry_schema.py` walks every shape enforcing it — so this is not a gap in the vocabulary that a sixth span shape could close. Widening §8.1 to admit content would trade the property that makes `/trace` safe to publish for one surface's convenience. A second *read* is the smaller change, and it is honest about being one. ADR-015's "one stream" claim now reads with a stated exception rather than quietly acquiring one.
2. **Live Firestore rather than a snapshot baked at seed time, because this belief is a moving target.** The tempting shape is a JSON file the seed script emits and the shell fetches: no route logic, no request-time credentials. It would be correct for about one item. Item 28's poisoning arc attacks this exact belief and the demo's closing shot is that it survived; item 29's Sweeper downgrades an expired belief to `UNKNOWN` and §10's sweeper row says the downgrade is "visible in the belief inspector". A snapshot would show the pre-attack chain during the attack and a fresh belief after the Sweeper had marked it stale — a surface that asserts state the store does not hold, which is the one thing §8 says these views must not do.
3. **§4.3 gets one implementation, and the breakdown is not a formatting concern.** `contributions()` returns one row per **distinct source class** carrying `base`, `age_days` and `weight`; `confidence()` multiplies those rows and nothing else. Computing the breakdown in the route, or shipping the weights table to the browser and doing it in JavaScript, would put the determinism boundary's published formula in a second place — and a breakdown that can disagree with the number it explains is worse than no breakdown, because ADR-002's whole defence is that a computed 0.94 is an audit trail. This is `telemetry.set_risk()`'s components-must-sum rule, applied to a product: `tests/test_policy.py` asserts `Π(1 − w) == 1 − confidence()` over a table, and `scripts/verify_belief_inspector.py` re-derives §4.3 from first principles rather than importing the function under test.
4. **Two versions, because §3.2's belief *is* a chain.** One version renders a one-row history that demonstrates nothing, and the item's title names the supersession chain. Two also makes this the first time §6.3's flip rule runs on the demo's own belief rather than on a scratch fixture: `AT_RISK` supersedes `FLAGGED` only because it clears `FLIP_THRESHOLD` **and** rests on `third_party_audit`, a class the chain did not already carry. The third evidence item therefore cannot be another reading of the first two, and that is a fact about the seed, not a preference — a restatement is refused at 0.5033, below the door.
5. **Through `policy.commit()`, with `now` eight days apart, and the numbers are whatever the weights produce.** ADR-009 and `tests/test_synthetic_company.py` already forbid the alternative: a seeded `status` field would be a belief with no evidence, no computed confidence and no signature, in a place recall never looks. The eight-day gap is load-bearing rather than decorative. Each version's own evidence is fresh at its own commit, so v1 clears 0.50 at 0.575; by the time v2 is judged those two items have decayed and the audit has not, giving 0.770. Back-date the pair instead and the arithmetic moves against you — at twelve days v1 scores 0.4495 and is refused `BELOW_THRESHOLD`. Committing both at the same instant would score higher (0.809) and render two rows with one date, which reads as a scripted double-write rather than a belief that changed.
6. **Create-if-absent with no `--reset`, for a sharper version of `seed_registry.py`'s reason.** That script refuses to reset because §3.4 says standing is never quietly forgiven. Here the stakes are the demo's closing shot: items 27 and 28 attack this belief and the point is that it survived, so a re-run that rewrote a poisoned-then-defended chain back to the fixture would erase the only thing that beat proves. The script refuses outright rather than skipping quietly, because a silent skip on a belief someone expected to be re-seeded is its own failure.
7. **Unauthenticated, on `/trace`'s reasoning rather than by analogy to it.** `/trigger` is guarded because a trigger spends model tokens against a fixed credit — an open endpoint there is a loop a stranger gets to run. Nothing here can be made to spend anything, the company is synthetic and hand-authored, and item 36 is a judge with a README and a cold browser. What bounds `/trace` is §8.1's redaction rule; what bounds this is that the data is fiction. `THREAT_MODEL.md` states that rather than letting "read-only" imply harmlessness.
8. **`BeliefNotFound → 404` and `BeliefStoreUnavailable → 503`, and they must not collapse.** §7.3 again, on the read side: a 404 tells a caller this entity has no beliefs, which is a claim a service cannot make while it cannot read the store. It matters concretely — item 28's closing shot is that `SUP-042` is still AT_RISK, and a route answering 404 when Firestore blinks would render that shot as the poisoning having worked.
9. **Both confidences are served, labelled.** The version document is immutable, so its `confidence` is frozen at commit while the evidence behind it keeps decaying. Serving only the stored number makes the decay clock a date with no consequence; serving only the live one makes the UI appear to contradict the append-only store it is inspecting. The breakdown has to be recomputed anyway, so the second number is free — and the two differing by exactly `2^(-age/30)` is the most direct demonstration that confidence is computed rather than asserted.

**What this deliberately does not do.** It does not render `flagged_by`, which **answers ADR-019's revisit clause — the one that names item 17 by number — with "not yet".** `SUP-042` is never retracted and no `authorizations/{id}` record cites it, so the field would be an empty array on every load, and a surface wired for a case it cannot show is untested code pretending to be a feature. Item 31's approval cards are the first surface with a flagged action to display, and the question ADR-019 raised alongside it — whether `audit.flag()` should emit a span so a flag is visible live rather than only in Firestore — is a §8.1 vocabulary change that belongs with the surface that needs it. It also adds no `statement` parameter to `policy.commit()`: §3.2 gives an ENTITY belief none, and item 23 is what first writes a belief that has one. And it does nothing about the expired clock beyond reporting it — the Sweeper is item 29's.

**A figure in §3.2 does not compute, and it is now marked.** §3.2 and the original spec render this belief at `conf 0.71` on one evidence item and `conf 0.94` on three. Neither is reachable under §4.3's published weights: the strongest base weight is 0.60 and the formula collapses a class to its least-decayed item, so one item caps at 0.60, and all five classes fresh cap at 0.9235. The figure is illustrative and stays as written — it is inherited verbatim from the spec, and rewriting it would diverge the two documents — but §3.2 now carries an as-built note giving the real numbers and saying plainly that the illustrated ones are not producible. ADR-002's defence of these weights is that they are inspectable and fixed; a canonical example that does not survive inspection undercuts it more than an admitted approximation does.

**What this costs:** one route, two to three Firestore reads per load (the version walk ADR-016 chose), and a UI that now has two data sources instead of one. The inspector rides the existing 15-second `/health` tick rather than the one-second `/trace` tick, because a belief changes on the order of once per demo and 60× the reads would buy nothing that items 28 and 29 need. `policy.py`'s per-process signing key is unchanged, so the seeded versions' signatures are unverifiable after the seed script exits — the same `ponytail:` debt the gateway carries, with Secret Manager as the same named upgrade path, and `THREAT_MODEL.md` says so rather than letting "signed" imply more.

**Revisit when:** item 28's poisoning arc wants the rejected write visible on this surface rather than only in the trace, at which point the route may need to serve refusals as well as commits; item 29's Sweeper writes `UNKNOWN(stale)` and the decay block needs a third state between "remaining" and "expired"; item 31's approval cards arrive and `flagged_by` finally has something to show (ADR-019's clause, deferred here); or a second surface needs a Firestore read, at which point "one route that reads the store" stops being a stated exception and becomes a second pattern worth naming.

**Alternatives considered:** carrying belief content on spans so the one stream serves everything (rejected — reason 1, and it would falsify the redaction rule that makes `/trace` publishable); a JSON snapshot emitted by the seed script and served statically (reason 2 — correct until item 28 writes to the belief, then silently wrong); a route plus a baked JSON fallback for a Firestore outage during judging (two code paths to keep in sync, insuring against a failure the rest of the demo does not survive either); computing the breakdown in the route handler or in the browser (reason 3); one `AT_RISK` version only (reason 4 — the simplest thing, and it renders no chain); three versions adding a re-affirmation (a third door to satisfy and more seed code, for one more row); writing the belief with `beliefs.append()` directly so the numbers could match §3.2's 0.94 (reason 5, and ADR-009 rejected exactly this shape); committing both versions at the same instant (reason 5); a `--reset` flag for between-takes rehearsal (reason 6); guarding the route with the trigger token (reason 7 — it would leave item 36's cold judge looking at an empty inspector); and rendering `flagged_by` now so item 19's first real retraction lights it up with no UI change (rejected above: untested code shaped like a feature).
