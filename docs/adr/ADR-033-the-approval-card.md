# ADR-033 — The approval card is rendered from a route that recomputes the arithmetic, and it is where "still no framework" is finally answered rather than deferred

**Status:** Accepted

**Decision:** §8.2's approval card is filled in `provenance/web/index.html` — the same single
static file, the same hand-written JavaScript, **no framework**, for the third time. It renders
from `GET /approvals`, which item 31 widens by **two derived keys per parked record**: `risk`,
computed by calling `risk.score()` on the parked proposal, and `hold_reason`, derived from a
request-time registry read. Both are additive beside the stored fields; neither is stored on the
record. The approve/deny buttons `POST /approvals/{id}` behind the trigger strip's existing
token field, **await the response**, and render what the gateway actually decided. Nothing about
the card is generated by a model, and the browser adds no number up.

**This ADR answers [`ADR-008`](./ADR-008-one-cloud-run-service.md)'s and
[`ADR-015`](./ADR-015-the-trace-ui.md)'s revisit clauses, which item 30 re-deferred here
([`ADR-032`](./ADR-032-the-approval-queue.md) §14).**

**Reasoning, in order of weight:**

1. **The arithmetic has one implementation and the card is not allowed to be a second one
   (primary reason).** §4.2's defence is that the number is a lookup anybody can check, and
   `risk.py` is where the lookup lives. A browser that recomputed `base + criticality + blast +
   irreversibility` from the proposal's four fields would be a second implementation of the risk
   table on the one surface whose entire job is to explain the first — free to drift, and wrong
   in a way nobody would notice until it mattered. This is [`ADR-021`](./ADR-021-the-belief-inspector.md)'s
   reason 3 for `policy.contributions()`, applied to a sum instead of a product: *"a breakdown
   computed anywhere else is a second implementation that can disagree with the figure the
   Policy Engine actually decided with."*

2. **The span stream cannot serve it, and the reason is the reason item 30 exists.** The
   gateway's `provenance.authorization.decision` span already carries the risk components, so
   reading them off `GET /trace` needs no backend change at all. It also breaks on exactly the
   case the approval queue was built for: ADR-015's buffer is in-process and bounded, a park is
   *designed* to outlive its process (item 30 proved it across two Cloud Run revisions), and
   `--min-instances=0` guarantees the meeting. A card that renders blank for item 36's cold
   judge is worse than no card, because it looks like the queue is empty.

3. **Storing the score at park time would store a conclusion, and a stale one.** ADR-032 reason
   3 keeps the record an *input* — the raw proposal dict — precisely because `_signing_key()` is
   per process and a park cannot have its own signature checked later. The same argument applies
   here with a second edge: **a park is exactly the window in which standing moves.** Item 28's
   whole arc is an agent degrading while its action waits. A `hold_reason` written at park time
   would say `RISK_THRESHOLD` about an action that is now held on standing, or the reverse. So
   the route re-derives both, in `gateway._re_decide()`'s order, and the card is told what a
   resume would decide *now*. **Whose standing, specifically, is the proposer's** — `subject`
   and `proposal.proposed_by`, never `routed_to`. The two are routinely different: the domain
   agent reasons about the incident, the Planner proposes the action, and `SUP-042`'s live park
   carries `routed_to: supply-chain-agent` beside `subject: remediation-planner@v3`. Reading
   `routed_to` reports a different agent's trustworthiness than the gateway will check at
   resume, and inverts item 28's beat outright. This shipped wrong and the deployed queue is
   what exposed it (ROADMAP item 31's live finding); the offline test passed because its
   fixture used one agent for both roles.

4. **`_HOLD_REASON` is a dict with `SUSPENDED` missing, not a branch.** Item 28's `_LEARNS_FROM`
   shape: the rule is the shape of the mapping. A suspended agent's parked action is not held
   any more, it is refused — `gateway.resolve()` denies it whatever the human answers — so
   `.get()` returning `None` is the card being told so, and adding a third string would be
   inventing a hold state that §2.1 does not have.

5. **Additive keys, because four things already read this route.** `scripts/verify_approval_queue.py`,
   the README's curl, item 30's tests and now the card all parse `GET /approvals`. Nesting the
   record under a key for a tidier response shape would have broken every one of them. This is
   the discipline `approver` took on `authorizations/` one item ago: optional on read, added
   beside, nothing moved.

6. **No optimistic update — and that is what makes the no-framework answer evidence rather than
   an assertion.** ADR-015 reason 5 named this precisely: *"item 31's approval card introduces
   client-side write state, which is the next honest test of reason 5."* It turns out not to.
   The buttons disable, the `POST` is awaited, and what renders is the `Decision` the gateway
   signed — outcome, stage, reason, what executed, the verification verdict, the belief written.
   An optimistic flip would have to hold a provisional verdict the server has not agreed to, on
   a surface whose entire claim is that **an LLM never decides what the organization does and
   neither does a browser**. The client-side state is two module-level variables: a repaint key
   and an in-flight flag. A build stage, a lockfile and a second toolchain in CI still buy
   nothing. **ADR-008's and ADR-015's clauses are answered, not re-deferred.**

7. **The queue polls at 5s, the registry tick.** Between the fleet view's 1s and the inspector's
   15s, for the registry panel's stated reason: a hold has to appear inside one narration beat.
   The route now does a `validate` + `score` + one registry read per parked record and the demo
   parks at most two, so this is a handful of documents every five seconds — the cost ceiling is
   a design constraint here rather than something audited afterwards.

8. **The panel repaints only when the queue changed.** A blind 5-second `innerHTML` rewrite
   would wipe whatever the approver is halfway through typing. The key carries the hold reason
   and the score as well as the id, so a standing change *during* a park still redraws — which
   is the one live update this surface must not miss. The answered verdict renders into a
   separate region the poller never touches, so it survives the record leaving the queue.

9. **"Plain language" is English for the enum values, and nothing more.** `tier1` becomes
   "tier-1 — the business runs on it"; `org-wide` becomes "everyone, company-wide";
   `reversible: false` becomes "no — this cannot be taken back". A hand-written prose explainer
   *per action class* was considered and rejected: it reads better and it is a fifth table keyed
   by `action_class` that no document specifies, maintained by hand, and one action class away
   from being wrong. The action class prints as itself. The "why" is the stored trigger facts
   plus the `entity_ids` the fleet reasoned from — every clause a stored field or a lookup-table
   label, which is what item 31's "generated from the risk table, never from a model" means when
   applied to a sentence rather than a number.

10. **A tampered park renders "not scored" rather than crashing the queue.** §3.1 checks tier,
    blast radius and reversibility against an authority that is not the proposal, so a lie about
    any of them is `SCHEMA_INVALID` and never reaches §4.2 at all (item 30's live finding, from
    the other side). One bad record must not take the whole panel down, so `_derived()` catches
    it and the card says so — the shape the ledger panel already uses for a decision denied
    before the risk table.

11. **A registry outage is a 503, not a card that cannot say why.** `/registry`'s posture one
    surface over. A card that renders a hold and cannot state its grounds asks a non-engineer to
    approve something on no stated basis, which is the one wrong answer this surface can give.
    §7.3, and the same argument that makes an unreadable queue a 503 rather than an empty one.

12. **One token, not two.** The card reads the trigger strip's existing `#f-token` field. Item
    30 deliberately gave `POST /approvals/{id}` `/trigger`'s guard *and its secret*, because a
    resume spends model tokens against the same fixed credit; a second input for one secret
    would be a second thing that can be empty on Oct 1. The approver name is prefilled
    `dana.ruiz` — the persona the README and item 30's live run already use — and editable.

**Boundary discipline still applies:** the card decides nothing and computes nothing. The route
reads `risk.score()` and the registry; `gateway.resolve()` remains the authority; the browser
renders. No LLM-produced number enters any of it, and no LLM produced a word of it either.

**What this deliberately does not do:** render `flagged_by` on the belief inspector. ADR-019's
and ADR-021's clauses both said "when item 17's belief inspector or item 31's cards need to
render `flagged_by`" — and item 31 turns out not to. `flagged_by` is written when a belief is
**retracted** (§6.4); a parked HOLD retracts nothing, and neither verdict on one does. The
clause is re-pointed rather than quietly satisfied: it is due when a **`REFUTED` verification
produces a real retraction** against a belief a ledger row already cites, which is the first
time the field has something to show. Also not done: a deny-reason field (`ApprovalRequest`
stays two fields, and the ledger records who answered, not why — no document asks for the
rationale); a `GET /approvals/{id}` detail route; any browser storage.

**What this costs:** one `action.validate()`, one `risk.score()` and **one Firestore registry
read per parked record per request**, on a route polled every five seconds. `GET /approvals`
gains a second failure mode — a registry outage now 503s a route that previously only depended
on the queue — which is a deliberate trade of availability for the card being able to state its
grounds. `index.html` grows by roughly 130 lines and its first `POST` that is not the trigger.
`tests/test_app.py` gains an item-31 block. Nothing is deployed, nothing bills while idle.

**Live reader finding (item 31's `verify:` line):** a non-engineer read the score-11 card cold
and said *"it stopped because of some compliance check and because the score was greater than 7
it stopped and asked."* The rule landed; the stakes did not — none of tier-1, org-wide or
irreversible came back, and "some compliance check" was the whole of what they took from the
action. Reason 9's rejected per-`action_class` prose table is *still* rejected for the reason
given there, but the finding is real. **Both cheaper changes shipped**, and neither adds a word
of editorial: rows that scored non-zero render emphasized and rows worth 0 do not — the
emphasis is `n ? "weighs" : ""`, read off the same arithmetic the row displays, so a 0-point
row is quiet because it is not why the action stopped — and the `success_predicate` moved
*below* the risk block as a dim footnote, since it is the longest line on the card and the only
model-written one, and above the arithmetic it competed for the attention the reader did not
spend on the rows. What is deliberately **not** done is explaining what an action class means;
that is still reason 9's table, and still refused.

**Revisit when:** two incidents can park concurrently and the panel wants ordering from
Firestore rather than a sort in the browser (ADR-032's own clause, from the read side); a
`REFUTED` verification produces the first real retraction and `flagged_by` finally has something
to render; or the card needs to show *answered* records as well as parked ones, at which point
`approvals.pending()`'s single-state query is the thing that changes, not this surface.

**Alternatives considered:** recomputing §4.2 in JavaScript (reason 1); reading the components
off `GET /trace` (reason 2); storing `RiskScore` and `DecisionReason` on the record at park time
(reason 3); a third `hold_reason` string for `SUSPENDED` (reason 4); nesting the record under a
key in the response (reason 5); a separate `GET /approvals/{id}` for the detail view (reason 5,
plus N+1 fetches on a polling panel); an optimistic approve that flips the card and reconciles
(reason 6); a framework to manage that state honestly (reason 6 — there is no state to manage);
a 1s tick (reason 7); a 15s tick, which would leave a hold invisible for most of a narration
beat; an unconditional repaint (reason 8); a per-`action_class` prose table (reason 9);
propagating an `ActionError` out of the route (reason 10); letting a registry outage render a
card with a blank hold reason (reason 11); a second token or a remembered one in browser storage
(reason 12 — and the deploy secret does not belong on a viewer's disk); a free-text deny reason
carried into the ledger (a wire, record and ledger change for something no document asks for, in
a rendering item); and rendering `flagged_by` here to close two clauses while the file was open
— which is ADR-021's own "untested code shaped like a feature", rejected there by name.
